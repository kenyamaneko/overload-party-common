# Overload Party — カード設計ガイド

> 新しいカードを設計・追加する際の文言・書式・パラメータの統一ルール。
> 既存カードの修正時にも本ガイドに準拠すること。

---

## 1. カードテーブルのカラム

カードタイプごとに CARDS.md で使用するテーブルカラムが異なる。

### コンピュート系リソース / AI/ML系リソース

```
| # | カード名 | タイプ | デプロイターン | スループット | 可用性 | 維持コスト | SLAペナルティ | 効果 | 元ネタ |
```

### DB系リソース / オブジェクトストレージ

```
| # | カード名 | タイプ | デプロイターン | Yield | 可用性 | 維持コスト | SLAペナルティ | 効果 | 元ネタ |
```

- DB系リソースおよびオブジェクトストレージはスループットを持たない。代わりに **Yield** を記載。
- **維持コスト (Maintenance Cost)** は全リソースに存在する。Resizable は MC×ランク乗数で固定。Serverless は MC=0（使わなければ無料）。
- **Elastic の MC 計算式:** `MC = ElasticBonus × maintenance_cost × rank_multiplier / baseStat`
  - ElasticBonus = 0（初期状態）なら MC = 0（フリーティア）
  - ElasticBonus が増加するほど MC もスケールする

### プラットフォーム

```
| # | カード名 | 種別 | 効果 | 元ネタ |
```

### アタッチメント

```
| # | カード名 | 装備先 | 効果 | 元ネタ |
```

### ストラテジー

```
| # | カード名 | Cost | 効果 | 元ネタ |
```

### インシデント

```
| # | カード名 | Cost | 効果 | 元ネタ |
```

### リアクティブ

```
| # | カード名 | 発動条件 | 効果 | 元ネタ |
```

## 2. サブタイプと区分

### タイプ欄の書式

Resource カードのタイプ欄は `サブタイプ (区分)` の形式で記載する。

| 書式 | 意味 | 例 |
|------|------|-----|
| `Compute (R)` | Resizable のみ | えくぼ |
| `Container (E)` | Elastic のみ | Egao Container |
| `Orchestrator (R+E)` | 両方 | 天気使い Kubernetes |
| `Object Storage` | 区分なし | エリス |
| `Database` | 区分なし | BingoQuery |

### サブタイプ一覧

**フロントエンド:** Compute, Container, Orchestrator, AI/ML, Serverless
**バックエンド:** Database, Object Storage, Cache DB

> **注意:** 旧 NoSQL サブタイプは Database に統合された。表示用の `resource_label` として "NoSQL" は残るが、カードタイプとしては Database として扱う。

### 区分の割り当て

区分は**カードごとに個別設定**。サブタイプに依存しない。同じ Database でも RDS は `(R)`、Autonomous DB は `(E)`、BigQuery は区分なし。

元のクラウドサービスの実際のスケーリングモデルに基づいて割り当てる。

| 区分 | 基準 |
|------|------|
| **(R)** | ユーザーが手動でサイズ/性能を変更するサービス |
| **(E)** | 負荷に応じて自動スケールするサービス |
| **(R+E)** | 手動変更 + 自動スケールの両方 |
| **—** | スケーリング操作がないサービス |

## 3. パラメータの数値規則

### 基本単位

すべてのパラメータは **100 の倍数** で設定する。

### Elastic 表記

Elastic カードの Yield / スループットは `base→上限` で記載する。

```
スループット 500→1100    ← Container の例
Yield 500→700     ← Autonomous DB の例
```

### Elastic オートスケーリング

Elastic カードは自動スケーリング（ElasticBonus）を持つ。各カードの YAML に `elastic_increment` フィールドがあり、トリガーごとに TP / Yield が増加する。

| ゾーン | トリガー | 増加対象 |
|--------|----------|----------|
| フロントエンド | 攻撃を受けた時 | スループット (TP) |
| バックエンド Compute | 収益化（Monetize）に使用された時 | スループット (TP) |
| バックエンド DB | 各エンドフェイズ | Yield |

- ElasticBonus は**累積**される（トリガーごとに `elastic_increment` ずつ加算）
- 上限: **MaxTP / MaxYield** または **baseStat × 2** のいずれか小さい方
- ElasticBonus = 0 の状態が初期値（フリーティア相当）

### パラメータ設計の優先順位

1. **実サービスの特性を正確に反映する**（最優先）。実際に高性能で安価なサービスがあれば、それをそのまま表現する
2. **ゲームバランスの調整**はその次に考える

### SLAペナルティの設計

SLAペナルティは、そのサービスが停止した際の**顧客への影響の大きさ**を表現する。ビジネス価値が高く、停止時の影響が甚大なサービスほどSLAペナルティが高い。

## 4. 効果テキストの書き方

### 効果名

**太字** で効果名を記載し、コロンの後に効果内容を書く。

```
**Reserved Instance (Optional):** Deploy 時に宣言で Budget を -200 する (Cost 200)。ただし交換不可
**Always Free:** small → medium のメンテナンスコスト増加を無効にする
```

### 効果名の命名規則

効果名は **実サービスに存在する用語（設定名・機能名・概念名）** を使用する。架空の名前やゲーム用の造語は避ける。

効果内容も元サービスの挙動と矛盾しないよう設計する。完全一致は不要だが、**誤解を招かない範囲での抽象化** は許容。

### 効果なしの場合

```
効果: —
```

ハイフン1つ（`—`、em dash）を使用。

## 5. 効果テキストの構造

効果テキストは **[前提] + [効果本体] + [制約]** の三部構成で書く。

- **前提**: 条件、トリガー、コストなど、効果が発生するための要件
- **効果本体**: ステータス変化、破壊、デプロイ、無効化など、実際に起こること
- **制約**: 回数制限など、効果の使用に対する制限

```
前提:     このカードが破壊された時に発動できる。
効果本体:  トラッシュからこのカードをデプロイする。
制約:     この効果は1ゲーム中に1回のみ使用できる。
```

前提・制約がないカードは効果本体のみ記載する。

### 5-1. 前提

#### 任意発動と強制発動

効果の発動がプレイヤーの意思で決まるか否かを厳密に書き分ける。

| 語尾 | 意味 |
|------|------|
| `発動できる。` | 任意発動。プレイヤーが発動するか選べる |
| `発動する。` | 強制発動。条件を満たしたら自動的に発動する |

```
デプロイ時に発動できる。[効果]     ← 任意: デプロイしても発動しない選択が可能
デプロイ時に発動する。[効果]       ← 強制: デプロイしたら必ず発動
```

#### 条件付き効果

条件と効果本体を文で分ける。

```
場に [対象] がある場合にのみ発動できる。[効果]
場に [陣営名] カード 3枚以上なら発動できる。[効果]
Budget ≤ 1000 の時のみ発動できる。[効果]
```

#### トリガー効果

トリガーと効果本体を文で分ける。

```
[対象] が破壊された時に発動できる。[効果]
[対象] が攻撃した時に発動できる。[効果]
攻撃時に発動できる。[効果]
デプロイ時に発動できる。[効果]
[対象] をデプロイするたびに発動する。[効果]
```

#### コスト付き効果

```
[コスト] を払って発動できる。[効果]
```

#### 破壊トリガー

何が破壊されたかを明記する。

```
このカードが破壊された時に発動できる。[効果]
場の [対象] が破壊された時に発動できる。[効果]
```

> **注意:** 「破壊」は可用性が 0 になった場合と「破壊する」効果による場合を指す。コストとしてのトラッシュや手札溢れによるトラッシュは破壊ではない。（詳細は RULEBOOK.md を参照）

### 5-2. 効果本体

効果本体は以下の種類に分類される。`する` = 強制、`できる` = 任意。

#### ステータス変化

スループット, 可用性, Yield, Budget, デプロイターン, 維持コスト, RC 等の増減・変動。

**加算・減算:**

```
スループットを +200 する
Budget を -200 する
```

**倍率:**

```
スループットを 2倍にする
可用性を半分にする
```
**一時効果:** 永続でない場合は、効果の前に持続期間を付ける。

```
このターンのみ、スループットを +200 する
2ターンの間、可用性を -400 する
```

#### 破壊

```
[対象] を破壊する
```

#### ドロー

```
リポジトリから x 枚ドローできる
```

#### デプロイ

```
[デプロイ元] から [対象] をデプロイできる
[デプロイ元] から [対象] をデプロイターン 0 でデプロイできる
```

デプロイ元: 手札、リポジトリ、トラッシュ 等。復活もデプロイの一種。

#### 無効化

```
[対象] を無効化できる
```

#### ダメージ

```
[対象] に x ダメージを与える
```

#### インサイト吸収

```
相手の Insight を x 吸収する
```

吸収した Insight は自分の Insightプールに加算される。

#### サーチ

```
リポジトリから [対象] を x 枚手札に加える
```

#### 手札に戻す

```
[対象] を手札に戻す
```

#### 使用制限

```
相手は [カードタイプ] を使用できない
```

#### リダイレクト

```
攻撃の対象を [対象] に変更する
```

#### 免疫

```
[対象] の対象にならない
```

#### 装備（Attachment）

Attachment カードの効果は装備先の Resource に適用される。

- `コンピュート系リソース` = フロントエンドのコンピュート要素（Compute, Container, Orchestrator, Serverless）
- `AI/ML系リソース` = フロントエンドの機械学習・深層学習要素（AI/ML）
- `DB系リソース` = Database（NoSQL 含む）+ Cache DB
- `オブジェクトストレージ` = Object Storage
- `バックエンドリソース` = バックエンドの要素全般（DB系リソース + オブジェクトストレージ）
- `Resource` = フロントエンド・バックエンドすべて

#### 効果の組み合わせ

複数の効果を組み合わせる場合は「し、」でつなぐ。

```
[対象] を無効化し、破壊する
```

### 5-3. 制約

効果の使用回数や適用範囲を制限する。効果本体の末尾に句点で区切って記載する。

```
[前提] [効果本体]。この効果は1ゲーム中に1回のみ使用できる。
[前提] [効果本体]。この効果は1ターン中に1回のみ使用できる。
```


### 5-4. 対象の指定

対象は以下の要素を順に組み立てる。

```
[所有者] + [ゾーン] + [陣営] + [数量]
```

#### 所有者

| 表記 | 意味 |
|------|------|
| `自分の` | 自分のフィールドのみ |
| `相手の` | 相手のフィールドのみ |
| （省略） | 両プレイヤーのフィールド全体 |

フィールド全体が対象の場合のみ省略する。

#### ゾーン

| 表記 | 範囲 |
|------|------|
| `フィールド` | フロントエンド + バックエンド + サポートゾーン |
| `フロントエンド` | フロントエンドリソース |
| `バックエンド` | バックエンドリソース |
| `サポートゾーン` | プラットフォーム・リアクティブ |
| 直接指定 | カード名やタイプ名で指定 |

直接指定の場合、以降の要素（陣営・数量）は省略する。

#### 陣営（任意）

陣営カードの効果で他カードを参照する場合に同陣営名を付ける（→ セクション 6）。

#### 数量

| 表記 | 意味 |
|------|------|
| `全て` / `全体` | 対象すべて |
| `選択した x枚` | プレイヤーが対象を選ぶ |
| `ランダムに x枚` | ランダムに対象を選ぶ |

#### 特殊な対象

| 表記 | 意味 |
|------|------|
| `このカード` | 効果を持つカード自身 |
| `装備先` | Attachment が装備されている Resource |
| `その〜` | 直前に言及した対象を再参照 |
| `他の〜` | 自分自身を除く同条件のカード |

#### 組み合わせ例

| カードテキスト | 分解 |
|--------------|------|
| フィールド全体 | [省略] + [フィールド] + [全て] |
| 自分のフロントエンド全体 | [自分の] + [フロントエンド] + [全て] |
| 相手のフロントエンドから選択した1枚 | [相手の] + [フロントエンド] + [選択した1枚] |
| 自分の SD バックエンドから選択した1枚 | [自分の] + [バックエンド] + [SD] + [選択した1枚] |
| Daikichi | [直接指定] |

## 6. 陣営制限ルール

### 原則

**陣営カードの効果が他のカードを参照する場合、同陣営に限定する。**

現実のクラウドでは、同じプロバイダのサービス同士は緊密に連携できるが、異なるプロバイダ間の連携にはコストや制約が伴う。陣営制限はこの「マルチクラウドの困難さ」をゲームメカニクスで表現するためのルール。陣営を跨いだシナジーを防ぎ、デッキ構築に陣営選択の意味を持たせる。

### 陣営制限しないもの

- **自己効果:** 発動カード自身のみに影響する効果
- **Neutral カード全般:**
- **既に固有名で限定されている効果:**

## 7. 複数効果の記載

1枚に複数の効果がある場合は、効果名ごとに太字で分けて**改行して複数行で書く**。

```
**Autopilot:** デプロイ時、即座に medium にスケールアップ
**Fleet:** 自分の場に他のしゅがーLab Orchestrator がいる時、このカードのデプロイターン 0
```

---

## 8. 元ネタ列

- カードの元になった実際のクラウドサービス名やセキュリティ概念を記載
- 架空の場合は `—` を記載
- 1つのカードに対して1つが基本。複合元ネタの場合は代表的なものを記載

---

## 9. カード番号（#）

- 全カード通し番号。`1` から始まる
- 新カード追加時は**欠番を埋めず、最大値 +1** とする
- 欠番（削除済みカード）はそのまま残す

## 10. 権利上のリスク

カード名・効果名・陣営名に使用する用語の商標リスク一覧。新規設計時に参照すること。

> **前提:** 本ゲームはクラウドサービスの教育的パロディであり、元サービスと競合する製品ではない。
> ただし商標権者が問題視する可能性は用語ごとに異なるため、リスクレベルで分類する。

### 固有名詞・一般名詞の判別リスト

クラウド関連で固有名詞か一般名詞か紛らわしい用語の一覧。

| 用語 | 判定 | 権利者・根拠 | 紛らわしい理由 |
|------|------|------------|--------------|
| Kubernetes / K8s | **商標** | CNCF 商標 | OSS として広く普及しているが名称は CNCF が管理。K8s 略称も同様 |
| Terraform | **商標** | HashiCorp 商標 | IaC の代名詞的存在だが固有の製品名 |
| Exadata | **商標** | Oracle 造語商標 | 一般語の組み合わせに見えるが Oracle 固有の造語 |
| RAC | **商標** | Oracle 商標 (Real Application Clusters) | 略称が一般的に見えるが Oracle 固有の製品名 |
| TPU | **商標** | Google 商標 (Tensor Processing Unit) | GPU と同列の汎用略語に見えるが Google 固有 |
| CUDA | **商標** | NVIDIA 商標 | GPU 関連の一般的略語に見えるが NVIDIA 固有 |
| Redis | **商標** | Redis Ltd. 登録商標 | 広く普及しており一般語と誤解されやすいが、明確な商標 |
| MySQL | **商標** | Oracle 商標（Sun 経由で取得） | 「My」「SQL」は各々一般語だが、組み合わせは Oracle の商標 |
| MongoDB | **商標** | MongoDB, Inc. 商標 | OSS だが社名=製品名=商標 |
| Nginx | **商標** | F5 Networks 商標 | 略語風で一般名詞に見えるが固有名。読みも独特（エンジンエックス） |
| Kafka | **商標** | Apache Software Foundation 商標 | 作家 Franz Kafka に由来するが、ソフトウェアとしては ASF 商標 |
| Spark | **商標** | Apache Software Foundation 商標 | 一般英語（火花）だが、データ処理文脈では Apache Spark を指す |
| Elasticsearch | **商標** | Elastic NV 商標 | 「Elastic」「Search」は各々一般語だが、組み合わせは商標 |
| Prometheus | **商標** | CNCF 商標 | ギリシャ神話由来で一般名詞に見えるが、監視ツールとしては CNCF 商標 |
| Ansible | **商標** | Red Hat (IBM) 商標 | SF 用語（ル・グウィン）由来で一般語に見える |
| Helm | **商標** | CNCF 商標 | 一般英語（舵）だが、K8s パッケージ管理としては CNCF 商標 |
| Pub/Sub | **商標** | Google 商標 | 「Publish/Subscribe」は一般パターンだが、「Pub/Sub」は Google の製品名 |
| GPU | **一般** | — | NVIDIA がマーケティングで普及させたが、現在は一般的な技術用語として定着 |
| Serverless | **一般** | — | AWS が普及させた概念だが、商標ではなくアーキテクチャの一般名称 |
| Container | **一般** | — | Docker が普及させたが、OS レベルの仮想化技術の一般名称 |
| SRE | **一般** | — | Google が提唱した概念だが、商標登録されておらず業界一般用語として定着 |
| GraphQL | **一般** | — | Meta (Facebook) が開発したが、Linux Foundation に移管。名称は自由に使用可 |

### 補足

- **効果名:** 実サービスの機能名を効果名として使用している（Reserved Instance, Autopilot, Always Free 等）。カード名ではなく説明的・教育的な用途のため、カード名よりリスクは低い
- **元ネタ列:** 実サービス名の記載は出典の明示（引用・参照）であり、商標使用には該当しない
- **Linux / Docker:** 現在未使用。今後も使用しない方針

## 11. チェックリスト

新しいカードを追加する際に確認すること:

- [ ] パラメータがすべて **100 の倍数** か
- [ ] 効果名は**実在するサービス用語**か（架空の造語でないか）
- [ ] 効果テキストが **[前提] + [効果本体] + [制約]** の構造に従っているか
- [ ] 任意発動（`できる`）と強制発動（`する`）を正しく書き分けているか
- [ ] 他カードを参照する効果に**陣営名**が入っているか（陣営カードの場合）
- [ ] 複数効果がある場合、**改行して複数行**で記載しているか
- [ ] Elastic カードの表記が `base→上限` になっているか（Yield も同様）
- [ ] R/E 区分が元サービスのスケーリングモデルと整合しているか
- [ ] SLAペナルティが顧客影響の大きさを反映しているか
- [ ] CARDS.md のテーブルカラムがカードタイプに合っているか
- [ ] カード名・効果名に**商標リスクの高い固有名詞**を使用していないか（→ セクション 10）
- [ ] カード総数サマリ（CARDS.md 末尾）を更新したか
