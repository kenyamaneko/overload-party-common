## 1. 基本方針

### 強み

- **ターゲット（ITエンジニア）がSNS拡散力の高い層。** 広告費をかけずにオーガニックで広がる可能性が高い
- **「わかる人にはわかる」ネタがバイラルを生む。** エンジニア同士の会話のきっかけになる
- **「ガチャなし」が差別化ポイント。** エンジニア層は課金モデルへのリテラシーが高く、誠実なモデルを評価する
- **「これからIT業界に入る人」にも刺さる。** 開発者自身が異業種からITに転職して人生を変えた当事者。その体験に基づく制作動機が、キャリアチェンジを考えている層の共感と興味を呼ぶ

### ターゲット

| 層 | 誰か | アプローチ |
|----|------|-----------|
| **現役ITエンジニア** | クラウド・インフラに日常的に触れている人 | 技術記事（Zenn / Qiita）、エンジニアあるあるネタ、資格系コンテンツ |
| **IT業界を目指す人** | キャリアチェンジを考えている社会人、IT系の学生、駆け出しエンジニア | 開発者ストーリー（note）、キャリア系メディア露出、「ゲームで学ぶクラウド」的な切り口 |
| **TCG・ゲーム好き** | 遊戯王・MTG・ポケカ経験者、モバイルゲーマー | ゲームメディア、インフルエンサー、プレイ動画 |

### 原則

- お金をかけず、時間と工夫で勝負する（個人開発の予算制約）
- サービス名は出さない。「わかる人にはわかる」レベルに留める
- 開発者自身のストーリーが発信価値になる — プログラミング・作曲・ゲームデザインを1人で手がける「ZUN（東方Project）型」の個人開発者像は、それ自体がメディアに取り上げられやすいストーリー
- **開発者の人生そのものが最大のコンテンツ** — バックオフィス → 音楽 → IT という異色のキャリアと、「ITスキルで人生が変わった」という実体験が、ゲームの制作動機に直結している（[第2章](#2-開発者ストーリー)参照）

## 2. 開発者ストーリー

このゲームの最大のマーケティング資産は、ゲームそのものではなく **開発者の人生ストーリー** である。

### 2.1 ナラティブ（語るべき物語）

```
大学（文学部）で小説を書き、文学賞に応募する日々
    ↓
卒業後、労務管理などのバックオフィス業務に従事（社労士・行政書士 合格済）
    ↓
ミュージシャンになりたくて大阪の片田舎から上京
    ↓
音楽制作会社で下積み。しかし生活は苦しかった
    ↓
音楽を諦め、給料を上げるためにIT業界へ転職
    ↓
猛勉強 → IPA高度6区分、AWS 5冠、GCP 5冠を取得 → 給料が上がった
    ↓
欲しかった楽器が買えるようになり、音楽活動を再開
    ↓
「IT業界が人生を変えてくれた」という感謝
    ↓
過去の自分のように迷っている人に、クラウド技術に親しんでもらいたい
    ↓
ITインフラを擬人化したカードゲーム「Overload Party」を制作
```

### 2.2 なぜこのストーリーが強いか

| 要素 | 効果 |
|------|------|
| **挫折と再起** | 「音楽を諦めた → ITで人生を立て直した → 音楽も取り戻した」という構造は普遍的に共感を呼ぶ |
| **異色の経歴** | 文学部 × 社労士/行政書士 × ミュージシャン × ITエンジニア。メディアが「面白い」と感じる希少性 |
| **動機の純粋さ** | 金儲けではなく「IT業界への恩返し」「迷っている人の背中を押したい」という動機が好感度を生む |
| **スキルの裏付け** | 「ストーリーも作曲もコードも契約書も1人でやれる」が単なるハッタリではなく、学歴・資格・実績で証明されている |
| **ターゲットとの共振** | 現役エンジニアは「勉強して人生を変えた」経験を自分と重ねる。これからIT業界に入ろうとしている人は「自分もこうなれるかも」と希望を持つ。両方の層に同時に刺さる |

### 2.3 ストーリーの使いどころ

| 場面 | 使い方 | 深さ |
|------|--------|------|
| **SNSプロフィール** | 1行:「バックオフィス → ミュージシャン → ITエンジニア。IT業界に恩返しするためにゲームを作っています」 | 浅 |
| **ティザーサイト「開発者について」** | 上記ナラティブを3〜5段落にまとめた自己紹介 | 中 |
| **note 記事（第1弾）** | 「なぜITエンジニアがカードゲームを作るのか — 僕がIT業界に感謝している理由」 | 深 |
| **プレスリリース** | 開発者の経歴を2〜3行で紹介。記者が「取材したい」と思う粒度で | 中 |
| **Podcast・インタビュー** | フルストーリーを語る。質問に応じて深掘り | 最深 |
| **リリース記事** | 「個人開発ゲームをリリースするまでの全記録」の導入部で人生の経緯を語る | 深 |

### 2.4 メディア露出の可能性

このストーリーはゲームメディアだけでなく、複数のジャンルのメディアに刺さる。

| メディアジャンル | 切り口 | 具体例 |
|----------------|--------|--------|
| **ゲームメディア** | 「元ミュージシャンのITエンジニアが作ったIT擬人化ゲーム」 | 4Gamer, ファミ通App, AUTOMATON |
| **技術メディア** | 「IPA高度6区分+クラウド10冠のエンジニアが個人開発」 | ITmedia, @IT, Publickey |
| **キャリア系メディア** | 「バックオフィスからITに転職して人生が変わった話」 | エンジニアtype, Findy, Wantedly |
| **音楽メディア** | 「元音楽制作会社スタッフが、ゲームBGMも全部自分で作るインディー開発」 | DTMer系メディア、note マガジン |
| **転職・学習系メディア** | 「異業種からIT転職→ゲーム開発。クラウドを遊びながら学べるアプリ」 | Progate Magazine, Schoo, TECH CAMP ブログ, paiza |
| **地方メディア** | 「大阪出身の個人開発者が東京で奮闘」 | 地方紙、地元テレビ局 |

### 2.5 語るときの注意点

- **自慢にならないトーンで。** 資格の羅列ではなく「苦しい時期があったからこそ今がある」という文脈で語る
- **音楽を「諦めた」ではなく「形を変えて続けている」。** ゲームBGMとして音楽制作を続けていること、ITのおかげで楽器が買えたことをセットで語る
- **「クラウドに親しんでほしい」が結論。** ストーリーの着地点は常にゲームの制作動機に帰着させる
- **バックオフィス時代も否定しない。** 社労士・行政書士の知識は契約書作成（イラストレーターとの契約等）にも活きている
- **文学部卒はゲーム制作の武器。** 大学時代に小説を書いて文学賞に応募していた経験は、ストーリー構成・キャラクターの性格付け・世界観の言語化に直結している。「プログラマーが無理に書いたシナリオ」ではなく「小説を書いてきた人が設計した物語」であることは品質の説得力になる。結果が振るわなかったエピソードも含めて語ると親近感が増す

## 3. リリース前スケジュール

2026年秋のリリースを前提に、逆算してマーケティング活動を計画する。

### 2026年 3月: 準備期

| 週 | やること | 詳細 |
|---|---------|------|
| 第1〜2週 | SNSアカウント開設 | Twitter/X に公式アカウントを作成。プロフィール・ヘッダー画像を設定 |
| 第1〜2週 | ティザーサイトの企画 | 構成・デザイン方針を決める（[第4章](#4-ティザーサイト)参照） |
| 第3〜4週 | 技術記事の第1弾を準備 | ゲーム開発の動機・設計思想に関する記事を下書き |
| 第3〜4週 | 広報担当の選定を開始 | 候補者のリサーチ（[第7章](#7-広報担当の起用)参照） |

### 2026年 4月: 認知の種まき

| 週 | やること | 詳細 |
|---|---------|------|
| 第1週 | **公式アカウントで初投稿** | 「ITインフラを擬人化したカードゲームを作っています」＋開発画面のスクリーンショット |
| 第1〜2週 | ティザーサイト v1 公開 | コンセプト紹介 + メールアドレス収集フォーム |
| 第2週 | 技術記事 第1弾を公開 | Zenn or note:「ITエンジニアがカードゲームを作る理由」 |
| 第3〜4週 | 週2〜3回の開発進捗投稿を開始 | UI のモックアップ、カードデザイン案、開発裏話 |

### 2026年 5〜6月: キャラクター公開期

Phase 1 のイラストが納品され始める時期。ここが最大の勝負どころ。

| 週 | やること | 詳細 |
|---|---------|------|
| イラスト納品ごと | **キャラクター公開ツイート** | 1キャラずつ公開。イラスト＋キャラ紹介＋能力の一部を見せる |
| 2週に1回 | 技術記事の継続 | WebSocket 対戦の仕組み、カードバランス調整の裏側等 |
| 6月中 | **陣営診断コンテンツ公開** | ティザーサイトに診断ページを追加。SNSでシェアされやすい仕掛け |
| 6月中 | 広報担当の起用開始 | SNS運用の引き継ぎ・連携開始 |

**キャラクター公開の間隔:** 1週間に1〜2体ペース。一気に出さず、期待感を維持する。

### 2026年 7〜8月: 盛り上げ期

| 週 | やること | 詳細 |
|---|---------|------|
| 7月 | ティザーサイト v2 更新 | 公開済みキャラクターのギャラリー、ゲームルールの紹介を追加 |
| 7月 | **プレイ動画の初公開** | 実際の対戦画面を30秒〜1分の動画で公開。「動いている」ことで期待感が跳ね上がる |
| 7〜8月 | インフルエンサーへの打診 | 技術系 YouTuber / VTuber にクローズドβテストへの参加を依頼 |
| 8月 | **事前登録の開始** | App Store / Google Play の事前登録機能を有効化。ティザーサイトからもリンク |
| 8月 | クローズドβテスト | 限定人数でテスト。フィードバック収集＋口コミ効果 |

### 2026年 9月: リリース直前

| 週 | やること | 詳細 |
|---|---------|------|
| 第1〜2週 | リリース日の告知 | 具体的な日付を発表。カウントダウン開始 |
| 第2週 | プレスリリース配信 | PR TIMES 等で配信。ゲームメディア（4Gamer, ファミ通App等）への掲載を狙う |
| 第3週 | インフルエンサーのプレイ動画解禁 | βテスト参加者に動画公開を許可 |
| 第4週 | **リリース** | 各プラットフォームで同時リリース |

## 4. ティザーサイト

### 目的

1. ゲームのコンセプトを伝える
2. 事前登録（メールアドレス収集）
3. 陣営診断コンテンツでバイラルを狙う

### ページ構成

```
ティザーサイト
├── トップページ（ヒーロービジュアル + コンセプト）
├── 4つの陣営紹介（キャラ公開に合わせて順次追加）
├── ゲームルール（簡易版）
├── 陣営診断（診断コンテンツ）
├── 事前登録フォーム
└── 開発者について
```

### v1（4月公開）

- トップページ: キービジュアル（仮でもOK）＋「IT技術を擬人化した戦略型カードバトル」のキャッチコピー
- 4つの陣営のテーマカラー＋簡単な説明（イラストなしでもシルエットや陣営ロゴで）
- 事前登録フォーム（メールアドレス収集）
- 開発者紹介（[第2章](#2-開発者ストーリー)のナラティブを3〜5段落にまとめる）

### v2（7月更新）

- 公開済みキャラクターのギャラリー追加
- ゲームルールの紹介ページ追加
- 陣営診断コンテンツ追加
- 事前登録のリンクを App Store / Google Play に切り替え

### 陣営診断コンテンツ

5〜7問の質問に答えると「あなたは○○陣営タイプ！」と診断される。

**質問例（エンジニアあるある寄せ）:**

| 質問 | 選択肢の方向性 |
|------|--------------|
| チームで一番大事なのは？ | 連携（SD）/ 安定（天気使い）/ スピード（Sugar）/ 精度（調律部） |
| 障害が起きたとき最初にすること？ | ログを見る / 切り戻す / 力技で突破 / 根本原因を特定 |
| 好きなアーキテクチャは？ | マイクロサービス / モノリス / サーバーレス / フルマネージド |
| 理想のデプロイ頻度は？ | 毎日 / 週1 / 必要な時だけ / 半年に1回完璧に |

**シェア機能:** 診断結果をTwitter/Xにワンクリックでシェアできるボタンを設置。「#OverloadParty」ハッシュタグを自動挿入。

### 技術スタック（ティザーサイト自体）

軽量に作る。凝りすぎない。

| 選択肢 | 備考 |
|--------|------|
| Next.js + Vercel | React ベースで慣れているなら。無料枠で十分 |
| Astro + Cloudflare Pages | 静的サイト特化。高速 |
| Hugo + GitHub Pages | 完全無料。Markdown ベースで手軽 |

## 5. SNS運用ガイド

SNSが苦手な人向けに、「何を・いつ・どう書くか」を具体的に示す。

### アカウント設計

| 項目 | 内容 |
|------|------|
| プラットフォーム | Twitter/X（メイン）。余裕があれば Instagram（イラスト特化） |
| アカウント名 | @overload_party（例） |
| 表示名 | Overload Party｜IT擬人化カードゲーム |
| プロフィール | 「ITインフラを擬人化した対戦型カードゲーム。ガチャなし。2026年秋リリース予定。開発: @[個人アカウント]」 |
| 固定ツイート | ティザーサイトへのリンク＋キービジュアル |

### 投稿カレンダー（週間）

無理のないペースで継続することが最重要。週3回で十分。

| 曜日 | 投稿タイプ | 例 |
|------|-----------|-----|
| 月 | **開発進捗** | 「今週実装した機能」「UIデザインの変更前→変更後」等 |
| 水 | **キャラクター・世界観** | キャラ紹介、カード能力の解説、陣営の設定 |
| 金 | **エンジニアネタ / 雑談** | エンジニアあるある、開発裏話、困ったこと |

### 投稿テンプレート

#### 開発進捗系

```
【開発進捗】

対戦画面のUIを大幅にリニューアルしました。
カードの能力テキストが見やすくなったのと、
フィールドのゾーン配置を直感的に変更。

Before → After で見るとこんな感じです。

#OverloadParty #gamedev #indiedev
```

#### キャラクター公開系

```
【キャラクター紹介】えくぼ ― SD陣営

笑顔で世界中にデータを届ける配達員。
状況に応じてサイズを変え、どんな荷物も運びこなす。

🎨 イラスト: @[イラストレーター名]

#OverloadParty
```

#### エンジニアネタ系

```
カードゲームのバランス調整をしてたら、
「本番環境でしか再現しないバグ」みたいな
微妙なコンボが見つかった。

これはこれでゲームの味になるのか、
それとも修正すべきか…。

#OverloadParty #gamedev
```

### 投稿のコツ

| やること | やらないこと |
|---------|-------------|
| 画像・動画を必ずつける（テキストだけの投稿はリーチが低い） | 宣伝臭の強い投稿（「今すぐ事前登録！」の連呼） |
| ハッシュタグは2〜3個（#OverloadParty #gamedev #indiedev） | ハッシュタグの大量付与（スパムに見える） |
| 他の開発者やエンジニアの投稿にリアクション・リプライ | フォロワー数を気にしすぎる |
| 失敗談や悩みも素直に書く（共感を得やすい） | 完璧な発信だけを目指す（続かなくなる） |
| 毎週同じ曜日・時間帯に投稿する（習慣化） | 不定期に大量投稿→長期間沈黙のサイクル |

### 投稿時間帯

エンジニアがSNSを見る時間:

| 時間帯 | 理由 |
|--------|------|
| **8:00〜9:00** | 通勤時間 |
| **12:00〜13:00** | 昼休み（最もエンゲージメントが高い） |
| **21:00〜23:00** | 帰宅後のリラックスタイム |

**推奨: 昼12時台に予約投稿。** Twitter/X の予約投稿機能を使えば、投稿を事前にまとめて設定できる。

### フォロワーの増やし方

広告を使わずにフォロワーを増やす方法:

| 施策 | 効果 | 手間 |
|------|------|------|
| **技術記事からの流入** | 高 | 中（記事の末尾にアカウントリンク） |
| **陣営診断のシェア** | 高 | 低（一度作れば自動で拡散） |
| **キャラ公開ツイートの定期投稿** | 高 | 低（イラスト完成ごとに1投稿） |
| **エンジニア系のハッシュタグで交流** | 中 | 中（#gamedev, #indiedev, #個人開発 等） |
| **他のインディー開発者との相互フォロー・交流** | 中 | 低 |
| **開発者個人アカウントからのリツイート** | 中 | 低 |

**最初の100フォロワーが一番難しい。** 技術記事の公開と同時にアカウントを紹介するのが最も効率的。1記事がバズれば数百フォロワーを一気に獲得できる。

## 6. 技術記事戦略

エンジニアに自然にリーチできる最強のコンテンツマーケティング。

### 記事のネタ候補

| テーマ | プラットフォーム | 想定リーチ |
|--------|----------------|-----------|
| 「なぜITエンジニアがカードゲームを作るのか — バックオフィス→音楽→ITの人生で気づいたこと」 | note | 非常に高（人生ストーリー × 技術。[第2章](#2-開発者ストーリー)がベース） |
| 「Go + WebSocket でリアルタイム対戦ゲームを作る」 | Zenn / Qiita | 高（技術的に需要がある） |
| 「React + Capacitor でモバイルゲームを作る」 | Zenn / Qiita | 中〜高 |
| 「YAML駆動のカードデータ管理とコード自動生成」 | Zenn | 中 |
| 「ガチャなしで成立するモバイルゲームの課金設計」 | note | 高（ゲーム業界の議論を呼ぶ） |
| 「個人開発ゲームのインフラ設計（GKE + Cloud SQL）」 | Zenn | 中 |

### 記事の構成テンプレート

```
1. 導入（なぜこのゲームを作っているか — 30秒で読める程度に）
2. 本題（技術的な内容 — 記事の9割はここ）
3. 締め（「こんなゲームを作っています」＋ ティザーサイト / SNS へのリンク）
```

宣伝は最後に1行だけ。記事の主体はあくまで技術的な価値提供。

### 公開スケジュール

月1本ペース。無理に増やさず、1本1本の質を重視する。

## 7. 広報担当の起用

### なぜ必要か

- 開発者がSNS運用に時間を取られると、開発が遅れる
- SNSが苦手な場合、投稿の質・頻度が安定しない
- 専門の人に任せた方がエンゲージメントが高くなる

### 求める役割

| 役割 | 内容 |
|------|------|
| SNS運用 | 週3回の投稿作成・予約投稿・リプライ対応 |
| コミュニティ管理 | Discord の運営（リリース後） |
| 素材準備 | 投稿用の画像作成（キャラ紹介カード、告知バナー等） |
| 企画 | 診断コンテンツ、キャンペーンの企画・実行 |

### 起用方法

| 方法 | 費用感 | メリット |
|------|--------|---------|
| **SNS運用代行（フリーランス）** | 月3〜10万円 | ゲーム業界に詳しい人を選べる |
| **インディーゲーム好きのアシスタント** | 月2〜5万円 | ゲームへの愛着がある人が見つかりやすい |
| **知人・友人に依頼** | 応相談 | コミュニケーションコストが低い |

### 探し方

| プラットフォーム | 備考 |
|----------------|------|
| Twitter/X | 「#ゲーム広報」「#SNS運用」で検索。インディーゲームの広報経験者を探す |
| ココナラ / ランサーズ | SNS運用代行のサービスを出品している人がいる |
| インディーゲーム系コミュニティ | BitSummit、TOKYO INDIE FEST 等のイベント経由 |

### 起用時の注意点

- **ゲームの世界観を理解してもらう:** PROJECT_PROPOSAL.md を共有し、陣営やキャラクターの設定を把握してもらう
- **投稿の最終確認は開発者が行う:** 特にキャラクター公開や重要告知は、開発者がチェックしてから投稿
- **NDA（秘密保持）:** 未公開情報を扱うため、簡易的なNDAを締結
- **投稿アカウントの管理:** アカウントの所有権は開発者に帰属することを明確に

### 起用のタイミング

**推奨: 2026年6月（キャラクター公開が始まるタイミング）。**

4〜5月は投稿頻度が低いので開発者自身で対応可能。キャラ公開が始まり投稿量が増える6月以降に広報担当がいると効果的。

## 8. LINEスタンプ展開

ゲーム内スタンプをLINEスタンプとして配信する。エンジニアが仕事のLINEグループで日常的に使うことで、ゲームの認知が自然に広がる。

### なぜ効果的か

- ゲーム内スタンプのネタ（「LGTM」「進捗ダメです」「仕様です」等）がエンジニアの日常会話でそのまま使える
- **ゲームを知らない人でも買う** — エンジニアあるあるスタンプとして単体で成立する
- スタンプにキャラクターが描かれているので、「このキャラ何？」→「Overload Party っていうゲームの」という会話が自然に生まれる

### 配信概要

| 審査期間 | 通常1〜2週間 |

## 9. 音楽を活用したマーケティング

開発者がプロレベルの作曲家であることは、インディーゲーム開発者として極めて強い武器。プログラミング・作曲・ゲームデザインを1人で手がけるスタイルは東方ProjectのZUNさんと同じ構造であり、それ自体がストーリーになる。

### 9.1 陣営テーマ曲

4つの陣営にそれぞれ固有のテーマ曲を制作する。

| 陣営 | 音楽の方向性 |
|------|------------|
| SD | 明るく軽快、冒険感のあるポップス |
| 天気使い | 荘厳・神秘的、オーケストラ + アンビエント |
| しゅがーLab | カラフル・攻撃的、エレクトロ / EDM |
| 調律部 | クラシカル・優雅、弦楽 + ピアノ主体 |

**マーケティングへの活用:**
- キャラクター公開ツイートにBGM付き動画を添える（イラスト + BGM で投稿の質が一気に上がる）
- ティザーサイトでBGMを流す
- プレイ動画の世界観演出

### 9.2 サントラ配信

ゲームリリース前にサントラを先行配信すれば、ゲーム本体のプロモーションになる。

| プラットフォーム | 費用 | 備考 |
|----------------|------|------|
| Spotify / Apple Music / YouTube Music | DistroKid 等で年$22程度 | 音楽ストリーミングからゲームへの導線 |
| Bandcamp | 無料 | インディー音楽の定番。価格は自由設定 |
| YouTube（公式チャンネル） | 無料 | 「作業用BGM」として1時間ループ動画を公開 |

**「Overload Party OST — 作業用BGM」** としてYouTubeに上げれば、エンジニアが仕事中に聴く → ゲームの認知につながる。作業用BGM動画は再生数が伸びやすいジャンル。

### 9.3 作曲プロセスの発信

| 施策 | プラットフォーム | 効果 |
|------|----------------|------|
| 作曲過程の動画（タイムラプス） | Twitter/X, YouTube | 「DTMer × エンジニア × ゲーム開発」というユニークな切り口 |
| 音楽制作の技術記事 | note | DTMer層（ゲーム開発者とは別の大きなコミュニティ）にもリーチできる |

記事ネタ例:
- 「ゲームBGMの作り方 — 4つの陣営にどう個性を持たせるか」
- 「個人開発ゲームの音楽制作ワークフロー」

### 9.4 キャラクターソング

リリース後、人気キャラが判明した段階でキャラソンを制作する。

**歌詞の方針: ITエンジニアネタを歌詞に織り込む。** キャラクターの個性と元ネタの技術要素をダブルミーニングで表現し、エンジニアが聴いて「わかる」と思える歌詞にする。

#### 歌詞の方向性（陣営別）

| 陣営 | 歌詞に織り込めるネタ | 曲調 |
|------|---------------------|------|
| SD | 「届けたいものがある」「世界中のどこへでも」（配達 × CDN/グローバル配信）、「つながる仲間」（マイクロサービス連携） | 明るいポップス |
| 天気使い | 「嵐が来ても守り抜く」（障害復旧）、「空は晴れる」（可用性99.99%）、「凍てつく吹雪の中で」（コールドスタンバイ） | バラード / 壮大なオーケストラ |
| しゅがーLab | 「甘い誘惑に気をつけて」（高コスト）、「一瞬で溶かしてあげる」（高スループット）、「スケールの限界なんてない」 | アップテンポEDM |
| 調律部 | 「完璧なハーモニーを奏でよう」（データ整合性）、「一音も外さない」（トランザクション）、「この旋律は永遠に」（耐久性） | クラシカル / 合唱曲 |

#### ボーカルの選択肢

| 方法 | 費用 | メリット |
|------|------|---------|
| 歌い手・シンガーに依頼 | 1曲 数千〜数万円 | 人間の声の表現力。歌い手のファンも巻き込める |
| VTuber とのコラボ | 応相談 | 双方のファンに認知が広がる。話題性が高い |
| 合成音声（Synthesizer V, CeVIO 等） | ソフト代のみ | 自分のペースで制作可能。コスト最小 |

#### 展開タイミング

| 段階 | 内容 |
|------|------|
| リリース前 | BGM・陣営テーマ曲（インスト）に集中 |
| リリース後 | ユーザーの反応を見て人気キャラのキャラソンを制作 |
| 将来 | 陣営ユニット曲、全キャラ集合曲 |

調律部は設定上「音楽」が世界観の中心にあるため、キャラソンとの親和性が最も高い。最初のキャラソンは調律部から始めるのが自然。

## 10. 資格を活かしたコンテンツマーケティング

開発者が IPA 高度情報処理技術者試験 6 区分（DB, NW, ES, SC, SA, AU）、AWS 認定 5 冠、Google Cloud 認定 5 冠を保有していることは、「この人が作った IT 擬人化ゲームなら本物だ」という強力な信頼の裏付けになる。

### 10.1 開発者プロフィールへの活用

ティザーサイト・SNSプロフィール・技術記事の著者紹介に資格実績を明記する。

```
開発者: ケン・ヤマネコ
文学部卒 → バックオフィス（社労士・行政書士）→ 音楽制作 → ITエンジニア
IPA 高度情報処理技術者 6区分合格（DB / NW / ES / SC / SA / AU）
AWS 認定 5冠 / Google Cloud 認定 5冠
ストーリー・作曲・プログラミング・ゲームデザインを1人で手がける個人開発者
```

**効果:** 「ガチの IT エンジニアが作った IT 擬人化ゲーム」としてのブランディングが成立する。エンジニアは資格の難易度を理解しているため、「この人すごい」→「どんなゲームだろう」という関心の導線になる。

### 10.2 資格系コンテンツの展開

| テーマ | プラットフォーム | 想定リーチ |
|--------|----------------|-----------|
| 「IPA 高度試験を6区分取って気づいたこと」 | Zenn / note / Qiita | 高（資格系は常に需要がある） |
| 「AWS と GCP を両方5冠取った人から見た両者の違い」 | Zenn / Qiita | 非常に高（クラウド比較は鉄板） |
| 「ネスペ（NW）の勉強法を現役エンジニアが解説」 | Zenn / note | 高（試験前シーズンに検索が伸びる） |
| 「資格で学んだ知識をゲームのキャラクター設定に落とし込んだ話」 | note | 高（ストーリー性 + 資格 + ゲーム） |
| 「セキスペ（SC）合格者が考えるゲームのセキュリティ設計」 | Zenn | 中（技術的価値が高い） |

**ポイント:** 資格記事は検索流入（SEO）が強い。試験の前後（4月/10月）にアクセスが集中するため、試験シーズンに合わせて公開すると効果的。

### 10.3 ゲームの信頼性への貢献

| 活かし方 | 内容 |
|---------|------|
| ストーリー・キャラクター | 文学部卒 → キャラクターの性格設計、世界観の構築、テキストの質が「エンジニアが書いた」レベルを超えている |
| カード設計の深み | 「DB 持ちがデータベースの擬人化キャラを設計」→ 元ネタの解像度が段違い |

| アーキテクチャの実績 | SA 保有 → ゲームのインフラ設計自体が名刺代わり |
