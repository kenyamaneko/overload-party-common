# ADR-072: shop の IAP webhook は Apple/Google それぞれの信頼モデルに応じて別方式で検証する

## ステータス

Accepted (2026-08-11)

## 結論

Apple と Google の IAP webhook (外部からの通知エンドポイント) は、それぞれの配信プロトコルが提供する信頼の起点に応じて別方式で受信者を検証する。Apple はペイロード自体に付与された署名を検証し、Google はリクエストを運ぶ配信基盤が付与するトークンを検証する。どちらも他サービスと共通の内部認証は経由させず、それぞれの方式で自己完結して requester を検証する。

## 背景・課題

Apple と Google は IAP 通知の配信方式が異なり、両者とも通知の発信元がゲームサービス群の外側にあるため、内部サービス間認証の枠組みをそのまま適用できない。

- Apple の通知はペイロード自体が署名されて届くため、ペイロードを検証すれば送信元の真正性を確認できる。
- Google の通知は push 配信を経由し、メッセージ本体には署名が無い。配信基盤が付与するリクエストの正当性を検証する以外に、送信元を確認する手段がない。

両エンドポイントを共通のインフラ層の認可 (呼び出し IAM) でまとめて保護する構成も検討したが、対象のホスティング環境はサービス単位でしか呼び出し IAM を評価できない。Apple 向けに未認証アクセスを許可すると、同じサービス上にある Google 向けエンドポイントの IAM 保護も同時に失われる。そのため、インフラ層の制御に頼らず、アプリケーション自身が requester を検証する必要がある。

## 不採用案

### インフラ層の呼び出し IAM で両エンドポイントを保護する

サービス間認証で使っている仕組みをそのまま流用できる利点がある。しかし呼び出し IAM はサービス単位の適用であり、Apple 向けに未認証アクセスを許可すると同じサービスの Google 向けエンドポイントも保護を失う。両者を同一の入口で保護する前提が成立しないため採用しない。
