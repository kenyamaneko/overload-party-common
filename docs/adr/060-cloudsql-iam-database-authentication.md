# ADR-060: Cloud Run から Cloud SQL への接続に IAM データベース認証を使う

## ステータス

Accepted (2026-07-25)

## 結論

Cloud Run 上の各サービスは、自身のサービスアカウントに対応する IAM ユーザーで Cloud SQL に接続する。

- 接続は Cloud Run の内蔵コネクタが提供するソケットを通す
- .NET には公式の接続ライブラリが無いが、battle だけ別の認証方式にはしない
- パスワードを持つ組み込みユーザーは使わない

どのサービスが接続しているかが DB 層まで通り、権限の付与と剥奪が IAM で完結する。接続のために保管しておく長期の秘密が無くなる。

## 背景・課題

GKE では cloud-sql-proxy をサイドカーで併走させ、自動 IAM 認証の指定で認証を代行させていた。Cloud Run の内蔵コネクタはソケットを提供するだけで認証を代行しない。移行後、接続文字列にユーザーもパスワードも指定していなかったため、既定のユーザー名で接続を試みて認証に失敗した。

Cloud SQL には既にサービスごとの IAM ユーザーが作られている。権限分離の設計は元からあり、移行で落ちたのは認証の配線だけである。

## 不採用案

### cloud-sql-proxy を Cloud Run のサイドカーとして併走させる

アプリを変えずに済み、得られる認証も IAM で同じになる。しかし Cloud Run が内蔵で提供する接続を、サービスごとに自前で建て直す形になる。起動時間とメモリと障害点がサービスの数だけ増え、運用対象を減らすという [ADR-056](056-retire-gke-gitops-return-to-cloudrun.md) と [ADR-058](058-gateway-on-cloudrun-single-instance.md) の目的に反するため採用しない。

### 組み込みユーザーとパスワードで接続する

実装は最も軽い。しかし全サービスが同じ権限で全スキーマへ到達するため、サービスが自身の所有するデータの唯一の管理者であるという境界がアプリ層でしか成り立たなくなり、監査ログでもサービスを区別できない。パスワードの保管とローテーションを永続的に抱えることにもなるため採用しない。
