# ADR-060: Cloud SQL への接続を IAM データベース認証に統一する

## ステータス

Accepted (2026-07-25)

## 結論

Cloud Run 上で動く全てのワークロード (サービスとジョブ) は、自身のサービスアカウントに対応する IAM ユーザーで Cloud SQL に接続する。

- パスワードを持つ組み込みユーザーは使わない
- .NET には公式の接続ライブラリが無いが、battle だけ別の認証方式にはしない
- スキーマを変更するジョブも同じ方式とし、必要な権限はその IAM ユーザーに与える
- 接続経路をどちらにするかは実装時に確かめて決める。認証方式の決定は経路によらず成り立つ

どのサービスが接続しているかが DB 層まで通り、権限の付与と剥奪が IAM で完結する。接続のために保管しておく長期の秘密が無くなる。

## 背景・課題

GKE では cloud-sql-proxy をサイドカーで併走させ、自動 IAM 認証の指定で認証を代行させていた。Cloud Run の内蔵コネクタはソケットを提供するだけで認証を代行しない。移行後、接続文字列にユーザーもパスワードも指定していなかったため、既定のユーザー名で接続を試みて認証に失敗した。

Cloud SQL には既にサービスごとの IAM ユーザーが作られている。権限分離の設計は元からあり、移行で落ちたのは認証の配線だけである。

一方で、スキーマ変更を行うジョブは組み込みユーザーとパスワードで接続しており、方式が二つに割れている。割れたままにすると、どちらの前提で書かれた接続処理なのかを読む側が判断できず、パスワードの運用も残り続ける。移行を機に一つへ揃える。

接続経路には、実行基盤が提供するソケットを使う形と、VPC を通して private IP へ直接繋ぐ形がある。既存のジョブは後者で動いている。どちらでも IAM 認証は成立するが、前者が自動で認証を扱うかは確かめていないため、経路の選択は実装時の検証に委ねる。

## 不採用案

### cloud-sql-proxy を Cloud Run のサイドカーとして併走させる

アプリを変えずに済み、得られる認証も IAM で同じになる。しかし実行基盤が内蔵で提供する接続を、ワークロードごとに自前で建て直す形になる。起動時間とメモリと障害点がその数だけ増え、運用対象を減らすという [ADR-056](056-retire-gke-gitops-return-to-cloudrun.md) と [ADR-058](058-gateway-on-cloudrun-single-instance.md) の目的に反するため採用しない。

### 組み込みユーザーとパスワードで接続する

実装は最も軽く、既存のジョブがこの形で動いている。しかし全てのワークロードが同じ権限で全スキーマへ到達するため、サービスが自身の所有するデータの唯一の管理者であるという境界がアプリ層でしか成り立たなくなり、監査ログでもワークロードを区別できない。パスワードの保管とローテーションを永続的に抱えることにもなるため採用しない。
