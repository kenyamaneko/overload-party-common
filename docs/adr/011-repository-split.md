# ADR-011: リポジトリ分割（Gateway のスリム化とドメイン分割）

## ステータス

Proposed (2026-04-10)

## 結論

事実上のモノリス化した Gateway から責務を引き剥がすため、Gateway を WS 通信の入口レイヤーとしてスリム化し、現在 Gateway に集約されているドメインロジックを複数の独立した Go サービス（いずれも Go 1.25、現行 Gateway と同じスタック）に分割する。境界がリポジトリとネットワークの両方で強制されるため責務混在が再発しにくく、ドメイン単位の独立デプロイ・ロールバックにより変更リスクが局所化する。クライアントが意識するエンドポイントは引き続き Gateway のみで、ADR-002 の Battle 分離と同じ発想・同じ通信方式（内部 REST）に統一される。

## 背景・課題

ADR-002 でバトルエンジンを C# サーバーとして分離して以降、ゲームロジックに関する責務は整理されてきた。一方で、`overload-party-gateway` (Go) 側には依然として多数の責務が集約されたままであり、コードベースの成長に伴って以下の問題が顕在化している。

- **責務の混在**: 現在の Gateway は WS 通信ハンドリング・認証検証に加え、アカウント管理、デッキ/カードロジック、マッチメイキング、ショップ/IAP、シナリオ解放判定までを 1 つのリポジトリ内に抱えている。ドメインの異なる機能が同じパッケージツリーに同居しており、変更時の影響範囲を見極めづらい
- **コードの追いにくさ**: ディレクトリ構造やパッケージ境界が「WS ハンドラから呼ばれる処理の寄せ集め」になっており、特定機能の仕様確認や不具合調査のたびに広範囲を横断する必要がある。コードベースが成長するほど、新規参画者・将来の自分にとっての認知コストが増えていく
- **変更リスクの増大**: 例えばショップ関連の修正がマッチメイキングやシナリオのコードと同一バイナリに閉じ込められており、デプロイ単位が大きくなるほどリグレッションの心配が広がる
- **Gateway に期待する役割の曖昧化**: チームとしては Gateway を「クライアントの単一入口となり、WS 通信のハンドリングとルーティング、認証検証に専念するレイヤー」として位置づけたい。しかし現状は事実上のモノリスになっており、この意図が実装に反映されていない

ADR-002 ではバトルエンジンを独立サーバーに切り出すことで同種の問題を解消しており、今回はその方針をゲートウェイ側に残った各ドメインにも延長する。

## 詳細

### 責務分担

#### ランタイムサービスリポジトリ

| リポジトリ | 責務 |
|---|---|
| gateway | WS 通信ハンドリング、ルーティング、認証検証 |
| account | ユーザー登録・設定・パスワードリセット |
| matchmaking | マッチキュー管理、マッチロジック、バトルへの引き渡し |
| shop | 課金連携 (Apple/Google)、購入管理、フラグ付与 |
| scenario | シナリオ解放判定、シナリオファイル配信 |
| card | カードマスターデータ管理、デッキバリデーション、カード一覧 |
| battle | バトルロジック（既存、ADR-002 で分離済み） |
| newsfeed | クラウドニュース収集・配信 |

newsfeed は他のサービスと異なり、バッチ処理ジョブとして **Cloud Run Jobs** 上で稼働する（共有 GKE クラスタには乗せない）。クライアントからのリアルタイム通信経路に含まれないため、ADR-013 の GKE ノード配置の対象外とする。

Gateway はクライアントからのリクエストを受け取り、認証トークンの検証を行ったうえで、対応する内部サービスへルーティングする薄い層に徹する。ドメインごとの実装・テスト・デプロイは各リポジトリに閉じる。

#### 非サービスリポジトリ (設計・共通資産・運用)

| リポジトリ | 責務 |
|---|---|
| common | 全リポジトリ横断の SSoT。ゲームデザイン定数・カードマスター・ファクション、全リポジトリが consume するゲームデザインパッケージ、横断設計ドキュメント、shared DB スキーマ |
| client | Mobile/Web フロントエンド (React + Capacitor) |
| scenario-assets | ストーリー・キャラクター・ビジュアル資料 |
| infra | Terraform 管理の Google Cloud リソース (Cloud SQL, IAM 等) |
| k8s | GKE デプロイ定義 (Kustomize) |
| ops | DB マイグレーションジョブ (psqldef) |
| analytics | Spanner → BigQuery パイプライン |

なお、マッチメイキングキューの永続化方式は ADR-010 で、DB スキーマのサービス別オーナーシップは別 ADR で、GKE への運用移行は別 ADR で、それぞれ扱う。本 ADR はあくまで「リポジトリとサービス境界をどう引くか」にスコープを限定する。

### 通信方式

- **サービス間通信**: 内部 REST API を用いる。ADR-002 で Gateway ↔ Battle 間に採用した方式と揃え、運用・デバッグ・実装の一貫性を保つ
- **クライアントの入口**: 外部（クライアント）からアクセスできるのは Gateway のみ。account / matchmaking / shop / scenario / card / battle は Gateway 経由でのみ到達可能とし、クラスタ内ネットワークに閉じる
- **例外: shop の Webhook エンドポイント**: Apple/Google の課金サーバからのコールバック（サーバー間通知）は、外部サービス側の制約上 Gateway 経由でルーティングできない。このため shop サービスには Webhook 受信用のエンドポイントのみ公開アクセスを許可する。ユーザートラフィックの入口は引き続き Gateway 一本に保ち、Webhook 用エンドポイントはパスとレート制限で明示的に区別する

### トレードオフ

- **サービス間 REST 往復のオーバーヘッド**: 同一プロセス内の関数呼び出しに比べてレイテンシと失敗モードが増える。ただし ADR-002 で Gateway ↔ Battle 間で既に許容している水準であり、ユーザー体験上のクリティカルパス（対戦中のリアルタイム通信）は引き続き Gateway ↔ Battle に閉じているため影響は限定的
- **運用対象リポジトリ数の増加**: 監視・シークレット管理・バージョニングの対象が増える。サービス間の依存バージョンずれにも注意が必要になる
- **CI/CD の複雑化**: リポジトリごとにビルド・テスト・デプロイパイプラインを整備する必要がある。共通化のパターン整備を別途進める
- **境界設計の責任**: 一度分割したドメイン境界を後から引き直すコストは高い。本 ADR で示した責務分担は、今後の学びに応じて見直す前提で運用する

### common リポの最終形

リポジトリ分割とパッケージ分割が完了した後、common リポには以下のみが残る。ランタイムコードや特定サービスに属する SSoT は一切持たず、「全リポジトリが参照する横断資産」に責務を絞る。

```
overload-party-common/
├── data/
│   ├── cards/*.yaml                 カードマスター（当面）
│   ├── factions.yaml                ファクション SSoT
│   └── game_design_constants.yaml   ゲームデザイン定数 SSoT
├── packages/
│   ├── game-design-constants/       (Go/C#/TS) Faction, DeckSize, Restriction, CardType, InstanceFamily, MatchType, StatType, ファクションメタ
│   └── card-data/                   (Go/C#/TS) Card / CardStats / PassiveEffect / VariantTypes 等の型のみ (データは card サービス経由)
├── scripts/                         code-gen + バリデーションスクリプト
├── db/
│   ├── schema_postgres.sql          shared スキーマのみ (game_config 等の横断マスタ)
│   └── seed/game_config.sql         shared スキーマの seed
├── docs/
│   ├── architecture/                横断設計書のみ (ARCHITECTURE / DATA_DESIGN / I18N / CI_CD 等)
│   ├── game_design/                 ゲームデザイン資料
│   └── business/                    ビジネス・法務資料
└── .github/workflows/               common 固有の publish パイプライン
```

#### common から移管されるもの

| 移管対象 | 移管先 |
|---|---|
| `data/cards/*.yaml` | 将来的に card リポへ移管を検討 (当面 common) |
| `data/mock/news` | newsfeed リポ |
| `data/mock/products` | shop リポ |
| `data/mock/starter_decks` | card リポ |
| `data/event_schemas.yaml` (バトルイベント部分) | battle リポ |
| `data/models.yaml` の各サービスセクション | 各サービスリポ |
| `docs/architecture/API_REFERENCE.md` / `WS_REFERENCE.md` 等の特定サービス契約ドキュメント | 所有サービスリポ |
| `db/schema_postgres.sql` の各サービススキーマ部分 | 各サービスリポ |
| `packages/gamedata` / `gamedata-dotnet` / `gamedata-npm` / `api` / `api-npm` / `devdata` のうちサービス固有部分 | 各サービスリポ |

残るのは「特定サービスに属さない領域」= ゲームデザイン (= ゲームのルール) と、全リポジトリが参照する契約・定数・ドキュメント・shared DB スキーマのみである。

### パッケージ分割との関係

本 ADR はリポジトリ・サービス境界の分割を扱うが、common リポ内の `packages/` 配下と SSoT YAML の配置についても同じ思想で再編する必要がある。その詳細な方針（移管の段階的ロードマップを含む）は独立した ADR として [ADR-015](015-package-split.md) に分離した。

- リポジトリ分割（本 ADR）がサービス境界を定義する
- パッケージ分割（ADR-015）はその境界に合わせて `packages/` / SSoT YAML / ドキュメント / DB スキーマの所有権を各サービスリポに移していく段階的ロードマップを定義する
- 本 ADR のステータスと ADR-015 のステータスは独立しており、リポジトリ分割は進んでもパッケージ分割はフェーズごとに後から追いかける想定である

## 不採用案

### 案1: Gateway 内部でのモジュール分割（現状維持＋整理）

Gateway リポジトリを単一のまま、`internal/account`, `internal/shop` のようにパッケージ単位で責務を切るアプローチ。

- メリット: リポジトリ数が増えず、CI/CD もそのまま。短期的なコストはゼロに近い
- 却下理由: パッケージ境界はビルド時の強制力が弱く、実際には DB 接続やユーティリティ経由で容易にクロスドメイン参照が発生する。これまで Gateway が肥大化してきた経緯自体が、この「内部分割だけでは責務が守られない」ことを示している。また、デプロイ単位は相変わらず 1 バイナリのままであり、特定ドメインだけを独立にリリース・ロールバックする自由度が得られない。内部モジュール分割は「強制力が弱い」という問題を解けないため、リポジトリ境界まで引き上げるコストを支払う価値があると判断した
