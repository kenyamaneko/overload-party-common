# ADR-047: ミューテーションテストの導入

## ステータス

Proposed (2026-06-20)

## コンテキスト

`rules/principles.md` の `[base] テスト方針` は「実装をなぞるテストではなく、仕様に従っていることを確認するテストを書く」を掲げている。しかしこれを機械的に検証する仕組みがフリートに存在しない。

カバレッジは「行が実行されたか」しか測らない。テスト内のアサーションを全て削除してもカバレッジは落ちないため、テストの検出力 (実装を壊したときテストが落ちること) は測れない。品質目標は後者であり、これを測るにはミューテーションテストが要る。

テスト言語は Go 9 リポ / C# 1 リポ (battle) / TypeScript 2 リポ (client, e2e) / Python 3 リポ (common, ops, newsfeed) に分散している。

(カバレッジ計測自体は本 ADR の対象外として別途 PR で導入する。本 ADR はミューテーションテストに限る。)

## 決定

ミューテーションテストを **パイロット先行・nightly report-only + on-demand** で導入する。

- ツールは Stryker 系で言語間の運用を揃えつつ、Go / Python は各エコシステム標準を採る:

  | 言語 | ツール |
  |------|--------|
  | Go | gremlins |
  | C# (battle) | Stryker.NET |
  | TS | StrykerJS |
  | Python | mutmut |

- 実行モデル: nightly scheduled で full run (report-only) + `workflow_dispatch` による on-demand 実行。PR ゲートにはしない
- パイロット: battle (Engine 層は純粋ロジックでミューテーション信号が濃い) + Go サービス 1 リポ。baseline スコアと CI パターンを確立してから残リポへ展開する
- 閾値: 初期は report-only。baseline 確定後に break threshold を意図的に昇格させる

### なぜ CI モデルを nightly に隔離するか

ミューテーションは mutant 1 体ごとにテストスイートを 1 回実行する。素朴に PR で全実行するとコストが `mutant 数 × スイート時間` で増大し、ADR-038 のコスト方針と正面衝突する。よって nightly に隔離する。

diff スコープの PR ゲートも検討したが、変更行しか mutate せず、変更外コードの検証力低下 (共通ヘルパーの弱体化など) を見逃す。これは「狭いゲート」であって「厳密なゲート」ではなく、完全性の誤認を生む。full を nightly で回す方が誠実である。

### なぜパイロット先行か

CI 設計 (閾値・除外・実行時間制御) の失敗を全リポに同時波及させないため。パイロットで型を固めてから fan-out する。

## 検討した代替案

### 案 A: PR ブロック (diff scope) にする

- メリット: 劣化を merge 前に検出できる (shift-left)
- デメリット: 毎 PR にコストが乗り ADR-038 と衝突する。変更行のみの部分ゲートは検証力低下の見逃しを生み、完全性を誤認させる
- 不採用理由: コストと部分ゲートの誤認。即時性は on-demand 実行で部分的に補える

### 案 B: 全リポへ一斉導入

- メリット: 早い
- デメリット: CI 設計の失敗が全リポに同時波及する
- 不採用理由: パイロットで型を固めてから fan-out する方がリスクが小さい

### 案 C: カバレッジ計測のみで足れりとする

- メリット: 導入コストが最小
- デメリット: カバレッジは空テスト (アサーションを欠いたテスト) を検出できず、品質目標である検出力に届かない
- 不採用理由: カバレッジとミューテーションは補完関係にあり、本 ADR の目的はミューテーションでしか達成できない

## 影響範囲

### パイロット 2 リポ (battle + Go サービス 1)

- ミューテーション用の nightly workflow と `workflow_dispatch` を追加する。ADR-038 に従い `timeout-minutes` / `concurrency` を設定し、各ステップに `name` を付与する

### common

- 本 ADR がミューテーションテスト方針の SSoT。各言語 lang ルールへのツール明記は人間運用領域のため、本 ADR では提案に留める

## 移行計画

1. 本 ADR を Accepted へ進める
2. ミューテーションをパイロット 2 リポ (battle + Go 1) に nightly + on-demand で導入し、baseline を取得する
3. パイロット評価後、残リポへ fan-out する。閾値ゲート化は baseline 確定後に別途判断する

## 残課題

- Go パイロットリポの最終確定 (純粋ロジックの比重が高いリポを選ぶ)
- 閾値ゲート化の判断 (baseline 取得後)
