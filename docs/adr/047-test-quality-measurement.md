# ADR-047: ミューテーションテストの導入

## ステータス

Proposed (2026-06-20)

## 結論

「実装をなぞるテストではなく仕様を確認するテスト」という方針を機械的に検証するため、ミューテーションテストを **パイロット先行・nightly report-only + on-demand** で導入する。テストの検出力 (実装を壊したときテストが落ちること) がフリートで計測可能になり、空テスト (アサーションを欠いたテスト) を検出できる。

- ツールは Stryker 系で言語間の運用を揃えつつ、Go / Python は各エコシステム標準を採る:

  | 言語 | ツール |
  |------|--------|
  | Go | gremlins |
  | C# (battle) | Stryker.NET |
  | TS | StrykerJS |
  | Python | mutmut |

- 実行モデル: nightly scheduled で full run (report-only) + `workflow_dispatch` による on-demand 実行。PR ゲートにはしない
- パイロット: battle (Engine 層は純粋ロジックでミューテーション信号が濃い) + Go サービス 1 リポ (純粋ロジックの比重が高いリポを選ぶ)。baseline スコアと CI パターンを確立してから残リポへ展開する
- 閾値: 初期は report-only。baseline 確定後に break threshold への昇格を別途判断する

## 背景・課題

`rules/principles.md` の `[base] テスト方針` は「実装をなぞるテストではなく、仕様に従っていることを確認するテストを書く」を掲げている。しかしこれを機械的に検証する仕組みがフリートに存在しない。

カバレッジは「行が実行されたか」しか測らない。テスト内のアサーションを全て削除してもカバレッジは落ちないため、テストの検出力 (実装を壊したときテストが落ちること) は測れない。品質目標は後者であり、これを測るにはミューテーションテストが要る。

テスト言語は Go 9 リポ / C# 1 リポ (battle) / TypeScript 2 リポ (client, e2e) / Python 3 リポ (common, ops, newsfeed) に分散している。

(カバレッジ計測自体は本 ADR の対象外として別途 PR で導入する。本 ADR はミューテーションテストに限る。)

## 不採用案

### PR ブロック (diff scope) にする

- メリット: 劣化を merge 前に検出できる (shift-left)
- デメリット: 毎 PR にコストが乗り ADR-038 と衝突する。変更行のみの部分ゲートは検証力低下の見逃しを生み、完全性を誤認させる
- 不採用理由: コストと部分ゲートの誤認。即時性は on-demand 実行で部分的に補える

### 全リポへ一斉導入

- メリット: 早い
- デメリット: CI 設計の失敗が全リポに同時波及する
- 不採用理由: パイロットで型を固めてから fan-out する方がリスクが小さい

### カバレッジ計測のみで足れりとする

- メリット: 導入コストが最小
- デメリット: カバレッジは空テスト (アサーションを欠いたテスト) を検出できず、品質目標である検出力に届かない
- 不採用理由: カバレッジとミューテーションは補完関係にあり、本 ADR の目的はミューテーションでしか達成できない
