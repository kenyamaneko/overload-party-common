# ADR-059: gateway の計時をインメモリ主・Redis 従で保持する

## ステータス

Accepted (2026-07-25)

## 結論

gateway が持つ対戦ごとの計時 (ターンと切断猶予) を、インメモリを主とし Upstash Redis に写しを置く形にする。

- 書き込みは状態が変わったとき (手番の切替、切断、再接続) だけ行う。残り時間ではなく絶対時刻の期限を書く
- 読み出しはインメモリに該当が無いときだけ行う
- 写しの書き込みに失敗しても対戦は続ける。警告を記録する
- インスタンス数の上限は 1 のまま維持し、接続の対応表は分散しない

プロセスが予期せず終了しても計時が連続し、切断したプレイヤーがクラッシュで猶予を稼げなくなる。切断の期限がプロセスの外に残るため、決着の規則を「切断した側の負け」にできる ([BDR-002](../bdr/002-disconnect-resolution.md))。

## 背景・課題

Cloud Run はインスタンスの終了を避けられない。公式には、処理中のリクエストは完了まで待つとしつつ、例外的に処理中のコンテナへシャットダウンを開始することがあると明記されている。gateway の計時はプロセス内にあるため、この終了とともに失われる。

失われて困るのは「どちらがいつ切れたか」だけである。接続そのものはプロセスの持ち物で外に置けず、盤面と手番は battle が DB に持ち、対戦の参加者は gateway が自身のスキーマに持つ。残るのは切断の期限だけで、これは接続が消えた後にしか使い道が無く、消えた後には誰も覚えていない。

matchmaking が既に Upstash Redis を使っており、依存の追加は新規ではない。

写しの書き込み失敗で対戦を止めると、写しのための依存が対戦の可用性を下げる。主はインメモリであり、写しが無くても対戦は成立する。「エラーをログだけして握りつぶさない」という規約の例外として扱うのは、失うものが復元能力だけで、進行中の対戦への影響が無いためである。

## 不採用案

### 切断時刻を DB に永続化する

gateway のスキーマに列を足す案。対戦が終われば無価値になる情報のためにスキーマと生成物を増やすことになるため採用しない。

### 何も持たず、戻ってきた時点から猶予を数え直す

外部依存が増えない利点があるが、プロセスが落ちるたびに猶予が最初からになり、切断した側がクラッシュで猶予を稼げる。切断した側を負けとする扱い (ポケモンカードゲームポケット、遊戯王マスターデュエル) からも離れるため採用しない。

### 接続の対応表ごと Redis に載せ、複数インスタンスで動かす

[ADR-058](058-gateway-on-cloudrun-single-instance.md) の不採用案のとおり、配信の中継と計時の所有権の管理を、同時接続の上限に達していない段階で先払いすることになるため採用しない。
