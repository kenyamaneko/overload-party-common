# ADR-013: GKE Autopilot から Standard への移行

**Status:** Proposed
**Date:** 2026-04-10

---

## 背景

現在、Overload Party のバックエンド（gateway, battle, shop, matchmaking など）は GKE Autopilot クラスタ上で稼働している。Autopilot を最初に選んだのは、ノード管理を Google 側に任せることでオペレーション負荷を抑え、セキュリティベースラインや自動アップグレードを標準で得たかったためである。初期段階ではワークロードの規模感も定まっておらず、Pod 単位課金のほうがスケール変動に追従しやすいという期待もあった。

運用を続けるうちに、想定していた前提が実態と乖離してきた。

- **単一ノードで足りている**: 現在のトラフィック規模では全サービスが 1 ノードに収まっており、当面（少なくとも半年〜1年スパン）はこの構成を維持する見込みである
- **Autopilot の利点を活かせていない**: ノードプールの自動拡縮・bin packing の最適化といった Autopilot の主要な価値は、複数ノード運用を前提とした機能であり、1 ノード運用では恩恵がほぼゼロに近い
- **Pod 単位課金が割高**: Autopilot の課金モデル（CPU/メモリ/ストレージの Pod requests 合算）は、同等のワークロードを Standard の VM 単位課金で動かすより明確に高い。単一ノード固定なら VM 課金のほうが素直に安い
- **リソース制約のチューニングがしづらい**: Autopilot ではノードレベルの sysctl・カーネルパラメータ・特殊な taints などに制限があり、今後 WebSocket 接続数やファイルディスクリプタのチューニングが必要になったときに逃げ道が少ない

併せて、ADR-011 のリポジトリ分割に伴うインフラ再構築が控えている。クラスタごと作り直すタイミングに合わせて移行するのが、ダウンタイムとオペレーションコストを最小化できる最適なタイミングである。

## 決定

GKE クラスタを **Autopilot モードから Standard モードへ移行** する。移行は ADR-011 のリポジトリ分割に伴うインフラ再構築と同じタイミングで実施し、新しい Standard クラスタを構築したうえで既存ワークロードを載せ替える。

### クラスタ構成

| 項目 | 値 |
|------|-----|
| モード | Standard |
| リージョン | asia-northeast1 |
| マシンタイプ | e2-standard-2 (2 vCPU / 8 GiB memory) |
| ノード数 | 1 |
| ノードプール | デフォルト 1 本のみ |

### サービス配置

全ゲームバックエンドサービス（ADR-011 で分割される gateway / account / matchmaking / shop / scenario / card / battle）を**同一ノード上に 1 Pod ずつ**同居させる。レプリカ数は当面いずれも 1 とし、HA は現段階では追求しない（ユーザー規模と SLO に見合わないため）。

外部公開は 1 つの Ingress に集約し、以下の 2 サービスのみ外部からアクセス可能とする。それ以外のサービスはすべて ClusterIP とし、gateway からの内部 REST 経由でのみ到達可能にする。

| サービス | レプリカ | Service type | 公開理由 |
|----------|---------|-------------|---------|
| gateway | 1 | Ingress (外部) | クライアントからの REST/WS エントリーポイント |
| shop | 1 | Ingress (外部) | Apple / Google からの購入 webhook 受信のため公開エンドポイントが必要 |
| account | 1 | ClusterIP | gateway からの内部 REST のみ |
| matchmaking | 1 | ClusterIP | gateway からの内部 REST + Upstash Redis Pub/Sub (ADR-012) |
| scenario | 1 | ClusterIP | gateway からの内部 REST のみ |
| card | 1 | ClusterIP | gateway / battle からの内部 REST のみ |
| battle | 1 | ClusterIP | gateway からの内部 REST のみ（既存、ADR-002） |

合計 7 Pod を 1 ノード (`e2-standard-2`: 2 vCPU / 8 GiB) に相乗りさせる前提であり、各サービスの resource requests はノード容量を超えない範囲で配分する。resource limits と requests の具体値は k8s マニフェスト側で管理し、実測に応じてチューニングする。

なお、newsfeed はバッチ処理ジョブとして **Cloud Run Jobs** 上で稼働するため、本 ADR のノード配置・サイジングの対象外である。

## コスト比較

同等ワークロード（2 vCPU / 8 GiB 相当）を両モードで動かした場合の月額目安。

| 項目 | Autopilot (現行) | Standard (移行後) |
|------|-----------------|------------------|
| 課金単位 | Pod requests (CPU/memory/storage) | VM (ノード単位) |
| 月額概算 | 約 $90〜$110 | 約 $49 |
| クラスタ管理費 | 含む（第 1 クラスタは無料枠あり） | 同左 |

Standard 移行によって月額でおおよそ半減する見込みである。数字はリージョン asia-northeast1・オンデマンド価格・1 ノード前提の概算であり、Committed Use Discount 等は考慮していない。

## 検討した代替案

### Autopilot を継続する

運用負荷は最小だが、単一ノード運用では Autopilot の価値をほぼ享受できず、コスト面のデメリットだけが残る。将来的にマルチノード運用に戻る可能性はあるが、少なくとも現状の規模感では明確に割高であり継続する積極的な理由がない。

### Cloud Run に移行する

完全サーバーレスで運用負荷は最小化できるが、gateway が長寿命 WebSocket 接続を持つという要件に Cloud Run が適合しない（リクエスト単位のライフサイクル、最大タイムアウト、コネクションアフィニティの制約）。バトル進行中のセッション維持を考えると採用できない。

### 複数ノードの Standard クラスタにする

HA（可用性）は向上するが、現状のトラフィックでは明確にオーバースペックでありコストも倍以上になる。現時点でのユーザー規模と SLO を考えると過剰投資であり、マルチノード化は必要になった時点で検討する。

## 結果

### 得られるもの

- **コスト削減**: 月額約 $49 まで圧縮でき、Autopilot 比でおおよそ半減する
- **VM レベルのチューニング自由度**: sysctl・カーネルパラメータ・ノード taints/labels を自分で制御できるようになり、WebSocket 接続数など将来のチューニングに備えられる
- **料金モデルの直感性**: VM 単位課金のほうが「何がいくらかかっているか」が読みやすく、FinOps 面でも扱いやすい

### トレードオフ

- **ノードの自己管理**: OS アップグレード・セキュリティパッチ・ノードプールのバージョン管理を自分で行う必要がある。GKE の自動アップグレードチャネルを有効化して運用負荷を抑える
- **単一ノードが SPOF**: ノード障害時にクラスタ全体が停止する。現状のユーザー規模と SLO（ベストエフォート）では許容範囲とするが、ユーザー数が増えた段階でマルチノード化を再検討する
- **dev/stg の自動停止運用は継続**: コスト最適化のため、既存の dev/stg 環境を 2 AM JST に自動シャットダウンする運用は Standard 移行後も継続する。Standard クラスタでもノードプールのサイズを 0 にすることで同等のコスト削減が可能である

### 移行手順

ADR-011 のインフラ再構築と同じ Terraform 適用タイミングで実施する。既存 Autopilot クラスタと並行稼働はさせず、新 Standard クラスタへの切り替えをもって旧クラスタは破棄する。詳細な移行手順は別途 runbook として overload-party-k8s / overload-party-infra 側で管理する。
