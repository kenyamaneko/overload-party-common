# ADR-084: Battle のレイヤー境界をビルド時に強制する

## ステータス

Accepted (2026-08-11)

## 結論

Battle サービスを、値オブジェクト層・ドメインロジック層・NPC 思考層・永続化層・ユースケース層・composition root 層という責務ごとに独立したプロジェクトへ分割し、依存を一方向に固定する。ドメインロジック層は外界 (DB・HTTP・外部サービス等) の実装を直接参照せず、必要な外界操作は自らの内部に interface として宣言し、実体は永続化層が実装として提供する。プロジェクト間の参照方向がそのまま依存の一方向性を表すため、ドメインロジックが外界の実装に依存する変更をコンパイルエラーとして検出できる。

共通の外部ライブラリ依存は、依存階層の最も浅いプロジェクトに一度だけ宣言し、それより深い層へは自動的な依存解決で伝播させる。各層が同じ依存を個別に宣言しないことで、依存の追加・削除箇所を 1 つに保つ。

composition root 層は、他の層が提供する実装を組み立てて注入する唯一の場所とする。composition root が直接参照するのは自らが組み立てる実装に限り、自動解決できる中間層は参照しない。これにより、composition root が組み立てる実装の一覧が参照リストからそのまま読み取れ、ドメインロジックが外界の実装を直接呼び始めるような境界の変更は参照リストの差分として見える。

## 背景・課題

ドメインロジックが外界の具体的な実装に直接依存しないという方針自体は、名前空間やディレクトリ構成のような論理的な区切りだけでも表現できる。しかし論理的な区切りは、その区切りを跨ぐ参照を書いてしまってもコンパイルが通ってしまうため、違反の検出をコードレビューに委ねることになり、レビューで見落とせば違反したまま取り込まれてしまう。この検出をコンパイラに任せられる構造にするかどうかの判断が必要だった。

## 不採用案

### 名前空間やディレクトリ構成による論理的な区切りに留める

却下。区切りを跨ぐ参照を書いてもコンパイルが通ってしまい、違反の検出をコードレビューに委ねることになる。レビューで見落とせば違反したまま取り込まれる。
