# ADR-044: reactive 効果の解決モデル再設計（トリガーの event 化とチェーン機構の不採用）

## ステータス

Accepted (2026-05-17)。末尾の Amendment (2026-05-17: 連動する変更の修正) を含めて現行方針とする

## 結論

reactive 効果がカードのテキストどおりの場面で発火しない問題を解消するため、解決モデルを次のとおり再設計する。

1. **`reactive` トリガーを廃止し、反応する出来事ごとのトリガー（`on_attack_declared` / `on_deploy` / `on_destroy` / `on_incident` / `on_damaged`）に分ける。** 各カードは、反応対象の出来事が起きた時点で発火する。
2. **`deploy` と `on_enemy_deploy` を `on_deploy` に統合する。** 自分/相手どちらのデプロイか、デプロイされたカード自身の効果か他カードの監視効果かは、guard 述語と card_type で判定する。
3. **発火のタイミングをトリガーで、発火の条件（攻撃者の faction、致死かどうか等）を guard で表す。**
4. **1 つの出来事につき発動するリアクティブ（card_type == `Reactive`）は、最も早くセットされた 1 枚のみ。** 発動後は表向き化してトラッシュへ送る使い切りとする。
5. **チェーンスタックは採用しない。** 実装済みだが一度も呼ばれていないチェーン機構と、空配列が往復するだけの DB カラムを削除する。

これにより、「破壊された時」「インシデント使用時」等のカードが、そのテキストどおりの場面で発火するようになる。

## 背景・課題

battle の reactive 効果がカードのテキストどおりに発火せず、[battle#56](https://github.com/kenyamaneko/overload-party-battle/issues/56) で表面化した。症状は次の 3 つ:

- **「破壊された時」系カードが、破壊が起きていなくても毎回の攻撃で発火する。**
- **インシデントに反応するカードが発火しない。** 反応する経路がそもそも無い。
- **サポートゾーン以外に置かれるカードが永久に発火しない。** 発火するかを調べる対象に入っていない。

原因は、これら異なる場面を `reactive` という 1 つのトリガーにまとめ、しかも攻撃宣言時にしかそのトリガーを判定していなかったことにある。破壊・インシデント・被ダメージといった他の場面には、発火する機会が無かった。

あわせて、チェーン機構が使われていない。実装済みだがゲームロジックから一度も呼ばれず、DB カラムには空配列が往復するだけだった。

[battle#54](https://github.com/kenyamaneko/overload-party-battle/issues/54)（reactive のプレイヤー選択ギャップ）は本解決モデルの上に乗るため、本 ADR が前提となる。

## 不採用案

### チェーンスタックを実装する

却下理由: reactive-on-reactive 禁止・カウンター罠なし・全自動発動という前提では、スタックがあっても観測できる挙動は変わらない。「キャンセル → ダメージ → 破壊」の処理順は一意に決まっており、LIFO のスタックでは表現できず、結局スタックの外で順序を管理する二重化になる。

### `reactive` を `reactive_on_attack` / `reactive_on_destroy` 等に細分化する

却下理由: 出来事ごとのトリガー分類を `on_*` ファミリと二重に持つことになる。リアクティブはカード種別であって、発火する出来事の軸ではない。

### `deploy` と `on_enemy_deploy` を別トリガーのまま残す

却下理由: 「リソースがデプロイされた」は単一の出来事。自分の効果か監視効果かは card_type と guard で表現でき、トリガーを 2 つに割る必然がない。
