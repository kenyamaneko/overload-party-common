# ADR-049: ローカル開発インフラをホストに公開せず compose 内部ネットワークで参照する

## ステータス

Accepted (2026-07-04)

## 結論

ローカル開発のインフラをホストに publish しない。サービスはインフラおよび他サービスを **compose 内部ネットワークのサービス名 DNS** で参照する。e2e が既に採用している結線形態にローカル開発全体を揃える。

compose を持つ各サービスリポの `docker-compose.yml` を次の形に揃える。

- インフラコンテナ (postgres / redis / pubsub / firestore) から `ports:` のホスト公開を削除する。
- サービス本体を compose のサービスとして起動し、接続先をサービス名 (`postgres` / `redis` / `pubsub` 等) に切り替える。
- ホストへ publish するのは、ホスト上のプロセス (ブラウザ・curl・Playwright) が到達する必要のあるサービス自身の API ポート (90xx) のみに限る。90xx は一意に採番済みで衝突しない。

これにより、ホストのポート空間にはインフラが一切現れなくなり、外部アプリ衝突・リポ間衝突の双方が構造的に消える。

## 背景・課題

ローカル開発でインフラ (PostgreSQL / Valkey(Redis) / Pub/Sub emulator / Firestore emulator) を動かす形態が現状 2 つある。

**形態 1: サービス単体起動 (`make run`)**
各サービスリポの `docker-compose.yml` はインフラコンテナのみを定義し、そのポートをホストに publish する。サービス本体は `make run` でホスト上に直接起動し (`go run ./cmd/server` 等)、`localhost:5432` 等でインフラへ接続する。

- Postgres `5432:5432`: account / battle / news / shop / scenario / support の 6 リポ
- Valkey `6379:6379` + Pub/Sub `8085:8085`: matchmaking / newsfeed の 2 リポ
- Firestore emulator `9041`: account / shop / scenario が `localhost:9041` を参照 (compose 外で起動)

**形態 2: e2e スタック (`pnpm compose:up`)**
`overload-party-e2e` の単一 compose が全サービス + 共有インフラ 1 セットをコンテナで起動する。各サービスは **compose のサービス名 DNS で内部接続** する (`host=postgres port=5432`、`UPSTASH_REDIS_URL=redis://redis:6379`、`PUBSUB_EMULATOR_HOST=pubsub-emulator:8085`、`ACCOUNT_SERVICE_URL=http://account:9005`)。

形態 1 の問題はインフラをホストに publish している点にある。ホストのポートは 1 台の OS で共有される有限資源なので、次の 2 種類の衝突を生む。

- **外部アプリとの衝突**: `5432` / `6379` / `8085` は広く使われるポートで、開発者が同時に動かす他プロジェクトと衝突しやすい。
- **リポ間の衝突**: 6 つの Postgres compose がすべて同じ `5432:5432` を publish するため、複数リポのインフラを同時に立てられない。

サービス本体のリッスンポート (9001-9009 等) は 90xx 系で一意に採番済みで衝突しない。残る衝突源はインフラのホスト公開だけである。

形態 2 (e2e) は既にこの問題を持たない。サービスもインフラも同一 compose ネットワーク内でサービス名 DNS により解決するため、インフラをホストへ publish する必要が本質的にない (e2e が publish しているのはホスト側のテストランナーが入口を叩くためであり、サービス間通信には使われていない)。本番も同じで、サービスが DB に `localhost` で到達することはなく、常に名前解決されたエンドポイントを使う。

### なぜホスト公開をやめ、内部 DNS 参照にするのか

**衝突の根本を消すため。** 衝突は「有限のホストポート空間を複数プロセスが取り合う」ことで起きる。インフラをホストに出さなければ取り合い自体が発生しない。ポート番号を非一般的な値へズラす対症療法 (代替案 A) と違い、番号選定・接続文字列との整合という継続的な管理が不要になる。

**本番と同じ接続形態になるため。** 本番でサービスが DB へ `localhost` で到達することはない。ローカルでも名前解決されたエンドポイント経由に統一することで、接続まわりのローカル/本番差異が縮む。

**既存の実績があるため。** e2e が同一機構で全サービスを結線しており、内部 DNS で全系が動くことは実証済みである。新機構の導入ではなく、既に片方で成立している形態への統一になる。

### `make run` (ホスト直起動) との関係

形態 1 は「アプリをホストで `go run`、インフラだけコンテナ」だったため、ホストのアプリがコンテナ内インフラへ届くにはホスト publish が必須だった。本決定はこの前提を変え、**ローカルの既定はアプリも compose 内で起動する** (e2e と同じ)。

高速な編集→再起動ループは、アプリコンテナにソースを bind-mount し、コンテナ内で `go run` することで維持する。ソースを書き換えてアプリコンテナを再起動すれば、Docker イメージを作り直さずに最新コードが反映される。ホスト直起動を残さないため、インフラをホストへ publish する動機自体が生じず、tracked な既定設定でホスト公開はサービス自身の API ポート (90xx) のみに保たれる。

## 不採用案

### 案 A: ホストポートを非既定番号へズラす

infra の host publish を残したまま `5432→55432` のように衝突しにくい番号へ変更する。

- メリット: compose の `ports:` と接続文字列を書き換えるだけで、アプリの起動形態を変えずに済む。
- デメリット: 外部衝突は減るがリポ間衝突は残る (6 リポが同じ番号を出す構図は変わらない)。番号選定と接続文字列との二重管理が恒常的に発生する。
- 不採用理由: 内部 DNS 化すれば「ホストにポートを出さない」ことで衝突の可能性自体が消え、番号管理も不要になる。対症療法を恒久設定にする必然性がない。

### 案 B: compose の host port を env でパラメータ化する

`ports: "${PG_PORT:-5432}:5432"` とし、開発者が各自 override できるようにする。

- メリット: tracked ファイルを編集せず個人環境で回避できる。
- デメリット: 既定値が `5432` のままだと、何も設定しない状態では衝突が既定で残る。回避を各開発者の手作業に依存させることになる。
- 不採用理由: 既定を conflict-free にしたい。高速ループはインフラをホストへ出さず、アプリの compose 内 `go run` + ソース bind-mount で確保するため、host port をパラメータ化して publish を残す必要がない。

### 案 C: 現状維持

- メリット: コストゼロ。
- デメリット: 外部衝突・リポ間衝突がともに残り、同時起動時の回避が開発者の手作業に残り続ける。
- 不採用理由: 本 ADR が解こうとしている問題がそのまま残る。
