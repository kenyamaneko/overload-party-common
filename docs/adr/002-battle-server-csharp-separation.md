# ADR-002: バトルサーバーの Go → C# 分離

## ステータス

Accepted (2026-02-15 推定)

## 結論

複雑化する対戦ロジックを Go から切り離すため、バトルエンジンを **独立した C# / .NET サーバー** (overload-party-battle) として分離する。ゲームロジックの変更が Gateway に影響しなくなり、効果システム (Op パイプライン) や NPC AI を C# の型システムで安全に構築でき、Gateway と Battle を独立にデプロイ・スケールできる。

## 背景・課題

当初、Gateway とバトルエンジンは同一の Go サーバーに同居していた。カードの効果処理・チェーン解決・NPC AI など、対戦ロジックの複雑さが増すにつれて、**Go の表現力では複雑なゲームロジックを記述・理解しづらい**という問題が顕在化した。

- **可読性の悪化**: Go はシンプルさを重視する言語であり、条件分岐・集合操作・型の表現が冗長になる。エフェクトチェーン解決やカード効果のバリエーション（パッシブ、リアクティブ、プラットフォーム、アタッチメント等）を書くと `interface{}` や map 操作、手動ループが大量に生じ、ロジックの意図が埋もれて理解しづらいコードになった
- **責務の肥大化**: 認証・デッキ管理・マッチメイキング・WS セッション管理とゲームロジックが混在し、変更影響範囲が広がっていた

C# を選んだのは、switch 式・LINQ・パターンマッチング・ジェネリクスなど、**ゲームルールを宣言的かつ型安全に書ける言語機能**が揃っているため。

## 詳細

### 責務分担

| 責務 | Gateway (Go) | Battle (C#) |
|------|-------------|-------------|
| 認証 (Firebase) | ○ | |
| プレイヤー・デッキ管理 | ○ | |
| マッチメイキング | ○ | |
| WS セッション管理 | ○ | |
| ゲームエンジン (ルール処理) | | ○ |
| NPC AI | | ○ |
| ゲーム状態永続化 | | ○ |
| エフェクトシステム | | ○ |

### 通信方式

- Gateway → Battle: 内部 REST API (`http://battle-server:9002/api/v1`)
- リクエスト/レスポンスは JSON、camelCase (内部) / snake_case (外部)
- Gateway はバトルサーバーのレスポンスをクライアントにプロキシする
- トレードオフ: サービス間通信のオーバーヘッド (REST 往復) が発生するが、対戦中のレイテンシ要件 (数百 ms) に対して十分許容範囲内

### C# 側のレイヤー構成

```
Models   → ドメインモデル・列挙型・定数 (依存なし)
Engine   → ステートレスなゲームロジック (Models に依存)
Npc      → NPC AI 戦略 (Models, Engine に依存)
Data     → リポジトリ実装: Mock (開発) / Pg (本番)
Service  → GameService ファサード (Engine, Npc, Data を統合)
Server   → ASP.NET Core Minimal API (エントリーポイント)
```
