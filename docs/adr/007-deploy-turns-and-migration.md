# ADR-007: DeployCost 廃止・デプロイターン導入・マイグレーション

**Status:** Accepted
**Date:** 2026-03-02

---

## 背景

現行ルールでは、カードのデプロイ時に Budget（開発コスト）を支払う仕組みだが、現実のクラウドにはデプロイ時に一括費用を払う概念はない。かかるのは技術者の「時間」であり、この違和感を解消したい。

また、教育目的として「どの技術がデプロイに時間がかかるか（＝設定が難しいか簡単か）」を体感させたい。

## 決定事項

### 1. DeployCost の廃止

- 全カードから `deploy_cost` フィールドを削除する
- Budget はデプロイに使わない
- Scale Up のコストも廃止（メンテナンスコスト増のみ）
- Budget 経済はメンテナンスコスト等の数値調整で成立させる

### 2. デプロイターン（deploy_turns）の導入

カードごとに `deploy_turns`（整数）を設定する。

#### メカニクス

- デプロイ時、カードは**裏向き**でフィールドに配置される
- `deploy_turns = 0`: 即座に表向き（従来と同じ挙動）
- `deploy_turns = 1`: 次の自分のターン開始時に表向きになる
- `deploy_turns = 2`: 次の次の自分のターン開始時に表向きになる
- 表向きになって初めて「稼働中のリソース」として扱われる

#### deploy_turns マッピング

| card_type | deploy_turns | 根拠 |
|-----------|-------------|------|
| **Serverless** | **0** | 即時デプロイがServerlessの存在意義 |
| **Container** | **0** | マネージドコンテナ（Cloud Run等） |
| **CacheDB** | **0** | マネージドRedis等 |
| **ObjectStorage** | **0** | S3バケット作成は即時 |
| **NoSQL** | **0** | DynamoDB/Firestore等マネージド |
| **Compute** | **1** | VM/インスタンス起動・設定 |
| **Database (RDB)** | **1** | マネージドDB（スキーマ設計等） |
| **Orchestrator** | **2** | K8sクラスタ構築は最も複雑 |
| **AI/ML** | **2** | MLパイプライン構築 |
| **Platform** | **2** | CI/CDパイプライン構築 |
| Attachment | なし | 即時（既存リソースへの設定追加） |
| Strategy | なし | 即時（一回きりの施策） |
| Incident | なし | 即時（事故は即座に起こる） |
| Reactive | なし | 即時（従来通り裏向きで伏せる） |

> deploy_turns はカード単位で個別設定可能。上記はカードタイプごとのデフォルト値。

#### 対象カード

deploy_turns を持つのは**リソースカード（Compute系・Data系）とPlatform**のみ。
Attachment / Strategy / Incident / Reactive は従来通り即時。

### 3. 裏向きカードのルール

| 側面 | ルール |
|------|--------|
| 攻撃対象 | **不可** |
| フィールド存在判定 | **いないものとみなす** |
| 攻撃の貫通 | Frontendに裏向きしかない場合、Backendを直接攻撃可能 |
| System-Down判定 | カウントしない（表向きが0枚 = System-Down） |
| メンテナンスコスト | **不要**（稼働していない） |
| Yield生成 | **しない** |
| パッシブ/プラットフォーム効果 | **適用しない** |
| スロット占有 | **する**（同じスロットに別カードは配置不可） |

### 4. スターター選択の廃止

従来の「Starting Resource 2体選出」フェーズを廃止する。

#### 理由

- deploy_turns 導入により、スターターでの即時デプロイは Serverless の強みを殺す
- deploy_turns=1 のカードでも1ターンで稼働するため、Serverless との差が小さすぎる
- 「スタートアップが初日から K8s を使うことはない」という現実に即したゲーム体験にしたい
- Serverless = 唯一の即時デプロイ手段、というアイデンティティを確立

#### 新しいゲーム開始フロー

1. デッキ 30 枚をシャッフル
2. 初期手札 5 枚をドロー
3. T1 開始（フィールドは空）

> デッキ構築で序盤戦略を組み立てる。Serverless を多く入れれば即時展開可能だがステータスは低い。
> サーチカードの充実により、引き運の緩和も図る。

### 5. System-Down の稼働実績フラグ と Launch Failure

スターター廃止＋デプロイターンにより、ゲーム開始直後は全プレイヤーの表向きリソースが 0 枚になる。
これを即 System-Down 敗北にしないため、**稼働実績フラグ**を導入する。

- 各プレイヤーに `has_had_active_resource` フラグを持たせる
- 一度でも表向きリソースがフィールドに存在したら `true` になる
- System-Down 判定は `has_had_active_resource == true` のプレイヤーにのみ適用
- 「まだ構築中」はシステムダウンではない

#### Launch Failure（ローンチ失敗）

稼働実績フラグの補完として、ローンチのデッドラインを設ける。

- 自分の **3 ターン目**（先攻なら T5、後攻なら T6）のエンドフェーズ終了時に判定
- `has_had_active_resource` が `false` のままであれば **Launch Failure** で敗北
- 内部定数: `launch_failure`

| 状況 | 判定 |
|------|------|
| 3 ターン以内に一度もリソースが表向きにならなかった | **Launch Failure** |
| T2 でリソース稼働 → T3 で全破壊 → フィールド空 | **System-Down**（稼働実績あり） |
| T4 以降でリソース全滅 | **System-Down** |

> ストーリー: 投資家から 3 ターン分の猶予をもらったが、サービスを立ち上げられなかった。資金は引き上げられ、スタートアップは解散。

### 6. マイグレーション（リソース移行）

既存リソースを SLA ペナルティなしで安全に退役させる仕組み。

#### 前提条件

- 新リソースが既にフィールドで**表向き（稼働中）**であること
- 旧リソースがフィールドで**表向き（稼働中）**であること
- **新リソースの deploy_turns >= 旧リソースの deploy_turns であること**（ダウングレード禁止）

#### ダウングレード禁止の理由

- K8s → Serverless への移行で SLA ペナルティ回避は「事業縮小」であり、ゲームのストーリー（事業を大きくしていく）に反する
- 無理に事業縮小するなら、ペナルティを伴う破壊で対応すべき
- deploy_turns が「規模・複雑さ」を既に表しているため、自然な制約

#### フロー

```
前提: 新リソース（表向き）、旧リソース（表向き）
  ↓
マイグレーション開始（メインフェーズのアクション）
  ↓  新リソース: ロック状態（攻撃・Yield生成・収益化など全て不可）
  ↓  旧リソース: 通常通り稼働
  ↓  1ターン経過（Platform等の効果で短縮可能）
  ↓
┌─ 成功（旧が生存）
│   → 旧リソース破棄（SLAペナルティなし）
│   → 旧スロットが空く
│   → 新リソースのロック解除
│
└─ 失敗（旧が移行中に破壊された）
    → SLAペナルティ発生（旧の破壊分）
    → 新リソースはロック解除して稼働継続
    → ストーリー: 引き継ぎ失敗でユーザー影響を出したが、新サービスは稼働開始
```

#### トレードオフ（プレイヤーの選択肢）

| 方法 | 所要ターン | SLAペナルティ | ダウンタイム |
|------|-----------|-------------|------------|
| **即破壊＋再デプロイ** | 新カードの deploy_turns のみ | **あり** | **あり**（破壊〜表向きまで空白） |
| **マイグレーション** | deploy_turns + 1 | **なし** | **なし**（旧が稼働し続ける） |

> 例: Container → Orchestrator へ移行
> - 即破壊: SLA ペナルティ + 2 ターン空白
> - マイグレーション: 2 ターン (deploy) + 1 ターン (migration) = 3 ターンだがノーペナルティ

### 7. Scale Up のコスト変更

- Budget コスト: **なし**（開発コスト廃止に伴い）
- 代わりに**メンテナンスコストがランクに応じて増加**する（既存ルール通り: ×1/×2/×3）
- これが実態に即している: スケールアップ時にお金はかからないが、ランニングコストが増える

## 影響範囲

### 削除するもの

- `deploy_cost` フィールド（全カードの stats から）
- `selecting` フェーズ（ゲーム状態）
- `select_starter` アクション
- `SelectStartersMessage` (WebSocket)
- `DeployCostFor()` ヘルパー関数
- スターター関連の AvailableActions 列挙
- Scale Up のコスト計算

### 追加するもの

- `deploy_turns` フィールド（カードデータ: YAML/JSON/Go/TS）
- `deploying_turns_left` フィールド（ResourceInstance: 残りデプロイターン）
- `face_up` フラグ（ResourceInstance / SupportInstance (Platform)）
- `has_had_active_resource` フラグ（GameState: per-player）
- `migrate` アクション（メインフェーズ）
- `migrating_from` フィールド（ResourceInstance: マイグレーション元の参照）
- 裏向き→表向き自動遷移（ドローフェーズまたはターン開始時）

### 変更するもの

- ゲーム開始フロー（スターターなし）
- `process_play_card.go`（Budget チェック削除、裏向き配置ロジック追加）
- `process_scale_up.go`（コストチェック削除）
- `win_condition.go`（System-Down に稼働実績フラグ追加）
- `turn.go`（ターン開始時の裏向き→表向き遷移処理）
- `process_attack.go`（裏向きカードの攻撃対象除外、Frontend 空判定の変更）
- `passive.go`（裏向きカードの効果除外）
- `available_actions.go`（selecting 削除、migrate 追加）
- カードデータ YAML（deploy_cost → deploy_turns）
- `constants.json`（新アクションタイプ、フェーズ等）
- RULEBOOK.md（全面改訂）
- クライアント型定義・UI
