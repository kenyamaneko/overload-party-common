# ADR-058: gateway も Cloud Run で実行し GCE を廃止する

## ステータス

Accepted (2026-07-25)

この ADR は [ADR-056](056-retire-gke-gitops-return-to-cloudrun.md) のうち gateway のホスティングに関する決定を置き換える。ADR-056 の他の決定 (battle と REST サービスの Cloud Run 化、Cloud SQL の継続、クラスタと GitOps の廃止) は維持する。

## 結論

gateway を GCE ではなく Cloud Run で実行し、常時起動する構成要素を無くす。

- gateway の Cloud Run サービスは最小インスタンス数を 0、最大インスタンス数を 1 とする。WebSocket 接続がある間だけプロセスが生き、接続が無い間はゼロへスケールする
- 対戦中の全員が切断した後に敗北を確定させる計時は、プレイヤーの次の操作を契機に決着させる方式へ移す
- gateway のマッチメイキング購読を Pub/Sub の pull 型から push 型へ変える

GCE のインスタンスとその周辺 (インスタンステンプレート、自己修復、起動時のコンテナ更新、静的 IP) が不要になり、維持し続ける実行基盤が無くなる。異常終了からの復帰は Cloud Run が担うため、可用性の仕組みを自前で持たなくてよい。未使用の環境では計算資源の費用が発生しない。

## 背景・課題

ADR-056 は gateway を GCE の Managed Instance Group で常時起動すると決め、Cloud Run 案を「WebSocket サーバはゼロへスケールできず、常時一インスタンスに固定する必要がある」ことを理由に不採用とした。このうち誤っていたのは、ゼロへスケールできないという点である。Cloud Run は WebSocket 接続を実行中のリクエストとして扱い、実行中のリクエストを持つインスタンスを回収しない。最小インスタンス数を 0 にしても、接続がある間はプロセスが維持される。一インスタンスに固定する点は正しく、本 ADR でも維持する。固定するのが常時動かす下限ではなく、同時に動く上限である点だけが違う。

残る論点は、接続が一つも無い間に CPU を必要とする処理が gateway にあるかどうかだった。実装を精査した結果、常駐する定期処理は無く、マッチ待ちとターンの計時はいずれも当事者が接続している間に限られる。例外は、対戦中の全員が切断した後に発火して敗北を確定させる計時だけである。これは接続が消えた後に動くことが目的なので、Cloud Run では成立しない。ただしこの計時が働かなくても、決着していない対戦が記録に残るだけで、プレイヤーは次の対戦を始められる。移行を妨げないため、決着の契機を計時からプレイヤーの操作へ移して解消する。誰を負けとするかは仕様の判断であり、BDR で別に決める。

インスタンス数の上限を 1 に固定するのは、接続の対応表と対戦ごとの計時が実行中のプロセスの中にあり、Cloud Run には特定のインスタンスへ接続を寄せる手段が無いためである。単一インスタンスが受けられる同時接続数はゲーム一本の規模に対して十分大きく、当面の制約にならない。

リクエストの最大実行時間に上限があるため、WebSocket 接続は一定時間で切れる。クライアントには自動再接続と対戦への復帰が実装済みで、gateway にも短時間の切断を猶予する仕組みがあるため、追加の対応は要らない。

GCE を選ぶと、単一のプロセスを動かすためだけにインスタンスとその周辺を維持し続けることになる。GKE を廃した目的は運用対象の削減であり、常時起動の要素を無くせるならその目的に沿う。

## 不採用案

### gateway を GCE で常時起動する (ADR-056 の決定)

ゼロへスケールできないという前提が成り立たないため、常時課金される計算資源と、自己修復やコンテナ更新の仕組みを維持する理由が無くなった。

### Cloud Run で最小インスタンス数を 1 に固定する

全員切断後の計時を今の実装のまま動かせるが、CPU を常時割り当てる必要があり、ゼロへスケールする利点を捨てて割増料金を払う形になる。計時の移設は決着の契機を変えるだけで済むため採用しない。

### 複数インスタンスへ拡張し、外部の共有ストアで接続を分散する

接続の対応表は共有ストアを介した配信で分散できるが、対戦ごとの計時は所有するインスタンスを決められず、Cloud Run には接続を特定のインスタンスへ寄せる手段が無い。同時接続の上限に達していない段階で、外部サービスへの依存と分散状態の管理を先に払うことになるため採用しない。

## Amendment: 2026-07-26 マッチメイキングの待ち行列の掃除が単一インスタンスに依存する

接続の消えた待機者を待ち行列から除く処理は、gateway が起動時に作る識別子が前回の起動と変わったことを契機に、待ち行列を空にする形で行う。

この仕組みは、同時に動く gateway が一つであること (最大インスタンス数 1) に依存する。上限を 2 以上にすると、一方の起動がもう一方の生きた待機者を消すため、仕組みごと見直しが要る。

[ADR-061](061-matchmaking-triggered-by-enqueue.md) が「ポーリングとは別の契機に移す」とした、期限切れの待機を取り除く処理は、この形で実装する。
