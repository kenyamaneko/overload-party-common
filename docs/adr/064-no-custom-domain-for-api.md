# ADR-064: API の入口に独自ドメインを使わない

## ステータス

Proposed (2026-08-05)

## 結論

API の入口に独自ドメインを割り当てず、Cloud Run が払い出す URL をクライアントから直接呼ぶ。

DNS のレコードと、その内容を環境の起動ごとに書き換える仕組みを維持しなくてよくなる。独自ドメインを Cloud Run の手前で成立させるための構成 (ロードバランサや中継) も持たずに済み、入口にかかる費用は Cloud Run の利用分だけになる。

## 背景・課題

GKE で運用していた頃は、公開ロードバランサに実 IP があり、環境の起動時にその IP を DNS のレコードへ書き込むことで独自ドメインを成立させていた。GKE を廃したときにこの仕組みが消え、レコードは仮の値のまま三環境とも固定されている。独自ドメインではどの環境にも到達できない。

Cloud Run は IP を持たず、Host ヘッダでサービスを振り分ける。自分の知らないドメイン名で来た要求には 404 を返す。独自ドメインを使うには、要求が Cloud Run へ届く前に Host ヘッダを書き換えるか、Cloud Run 側にそのドメイン名を登録する必要がある。

API を呼ぶのは Capacitor で作るスマートフォンアプリだけで、宛先はアプリのバンドルに焼き込まれ、一般ユーザーの目には触れない。Cloud Run が払い出す URL はサービスとプロジェクトとリージョンから決まり、サービスを作り直しても変わらないため、焼き込む値として安定している。独自ドメインを必要とする実体が他に無いことも確認した。

## 不採用案

### Cloud Run のドメインマッピングを使う

費用はかからないが、Google が遅延の問題により本番向けではなく正式版でも対応しないと明記しているため採用しない。

### Cloudflare の Origin Rules で Host ヘッダを上書きする

DNS を管理している Cloudflare で宛先を書き換えられるが、この機能は最上位の契約プランでしか使えない。ドメインのために契約を上げる費用は方針に合わないため採用しない。

### Cloudflare Workers で中継する

無料の範囲で Host ヘッダを付け替えられるが、一日あたりの要求数と一要求あたりの CPU 時間に上限があり、API の通信すべてがこの上限に縛られるため採用しない。

### 外部ロードバランサを置く

Google が推奨する方法で機能上の制約は無いが、環境ごとに常時課金される。ゼロへスケールする構成に寄せて固定費を削ってきた方針と釣り合わないため採用しない。
