# ADR-075: card のパック配布は冪等 API ではなく前段の重複防止ガードで扱う

## ステータス

Accepted (2026-08-11)

## 結論

card のカードパック配布は、配布処理自体を冪等にするのではなく、Pub/Sub イベント処理の前段で重複配信を検知して弾くガードとして扱う。配布 API は「呼ばれた回数ぶん加算する」非冪等な契約のままとし、重複防止は配布トランザクションとは別のイベント単位の記録によって at-least-once 配信を実用上の重複無しに近づける。イベント記録と配布処理は同一トランザクションにまとめない。記録の直後に配布処理がクラッシュする窓ではごく稀に二重加算が起こりうるが、イベント配信の再送間隔に対して実用上の影響は小さいと判断し許容する。

## 背景・課題

Pub/Sub は at-least-once 配信のため、同一イベントが複数回配送されうる。配布 API 自体を「同じ内容を要求されたら結果が変わらない」冪等な形にする案と、配布処理は非冪等なまま重複配信だけを弾く案の 2 通りを検討した。

配布処理は、シーズン報酬や補填のように「同じプレイヤーに同じカードをもう一度配りたい」正当なリクエストも受ける必要がある。リクエスト内容の同一性で冪等性を判定する設計にすると、この正当な再配布と誤配送起因の重複を区別できなくなる。

重複防止の記録と配布処理を単一トランザクションにまとめる案もあるが、配布処理は独自にトランザクションを管理しており、これを重複防止の記録と同一トランザクションに合わせると、配布処理側の責務分界が壊れる。

## 不採用案

### 配布 API 自体を冪等にする

却下。「同じ内容の配布をもう一度行いたい」正当なユースケース (シーズン報酬・補填等) と、誤配送による重複を区別できなくなる。

### 重複防止の記録と配布処理を単一トランザクションにまとめる

却下。配布処理が独自にトランザクションを管理する既存の責務分界を壊す。
