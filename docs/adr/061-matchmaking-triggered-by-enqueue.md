# ADR-061: マッチングの契機を定期実行から待機者の登録へ移す

## ステータス

Accepted (2026-07-25)

## 結論

マッチングの試行を、一定間隔で回るループではなく、待機者の登録を契機に行う。

- 登録を受けた処理の中でマッチングを一度試みる
- 期限切れの待機を取り除く処理は、別の契機に移す

リクエストの外で CPU を必要とする処理が無くなり、未使用時にゼロへスケールする構成と両立する。外部キューへの操作数が実際の利用に比例し、誰も待っていない時間の費用が無くなる。

## 背景・課題

マッチングは一定間隔で待ち行列を走査するループとして実装されている。待ち行列が変わるのは登録と取り消しのときだけで、何も起きていない間も外部キューを叩き続ける。

外部キューは操作数に応じた従量課金であり、この構造では費用が利用実態から乖離する。実際に開発環境でレート制限に達し、サービスが起動できなくなった。

さらに、[ADR-056](056-retire-gke-gitops-return-to-cloudrun.md) で移した先の実行基盤はリクエストの処理中しか CPU を割り当てないため、背景で回るループは進まない。移行にあたって洗い出したイベント購読の pull 型と同じ構造の問題が、マッチングのループにも残っていた。

待機者が増える瞬間は登録のときだけである。そこで試せば、成立の判定に不足は無い。

## 不採用案

### 走査の間隔を延ばす

操作数は減るが、待たせる時間が延びる。リクエストの外で CPU を必要とする構造も変わらないため、移行先で動かない点が解決しない。

### 最小インスタンス数を 1 にしてループを維持する

ループは動くが、常時課金される計算資源が戻る。常時起動の要素を無くした [ADR-058](058-gateway-on-cloudrun-single-instance.md) の判断と逆を向くため採用しない。

### 外部キューの通知機能で別プロセスを起こす

登録を購読して起こす案。購読を続けるプロセスが常駐している前提になり、背景ループと同じ理由で移行先では成立しない。登録の受け口が既に同じサービスにある以上、間に通知を挟む必然性も無い。
