# ADR-063: Cloud Run 構成に監視とアラートを置く

## ステータス

Proposed (2026-08-03)

[ADR-056](056-retire-gke-gitops-return-to-cloudrun.md) と [ADR-058](058-gateway-on-cloudrun-single-instance.md) が定めた Cloud Run 構成を前提とする。

## 結論

Cloud Run で動く全てのサービスに、Cloud Monitoring が標準で出すメトリクスを条件とするアラートを当てる。監視するのは、要求が失敗したこと (5xx 応答)、応答が遅いこと、ERROR ログが出たことの三つである。あわせて環境ごとに月次の予算アラートを置く。

これにより、Cloud Logging に溜まるだけだったエラーと、増えても分からなかった費用に気づけるようになる。アプリがメトリクスを出す実装を持たなくても条件を組めるので、監視を始めるために各サービスへ手を入れる必要もない。

- Cloud Run のジョブはサービスと別のメトリクスに乗るため、実行が失敗したことを捉えるアラートを分けて当てる
- アラートの定義は overload-party の各環境のプロジェクトに置く。アプリの監視はアプリ側が持つ
- ERROR ログのアラートは単発では発報させない。5xx を返す障害は ERROR ログにも現れるので、両方を単発で発報させると一件の障害で通知が二通届く
- dev を含む三つの環境すべてを対象にする。通知の届かない環境を作らない。dev と stg は動作確認でわざとエラーを起こすため、許容する件数を緩める形で扱う
- 予算は超過しても使用を自動で止めず、通知だけを行う
- 通知先はメールとする。Slack へ送るための設定は置くが、有効にはしない
- 全サービスのログ形式を、Cloud Logging が severity を解釈できる JSON に統一する。severity で絞るアラートはこれが成り立つことを前提とする

## 背景・課題

Cloud Run へ移った時点で、稼働中のサービスに対する監視は一つも無かった。エラーは Cloud Logging に溜まるだけで、それを人へ知らせる仕組みが無かった。実際に dev のデプロイが三週間失敗し続けたが、誰も気づかないまま過ぎている ([#267](https://github.com/kenyamaneko/overload-party-common/issues/267))。費用も同じで、増えたことを知る手立てが無かった。

GKE 構成では、ワークロードのログがブランド側のプロジェクトに集まり、そこから各環境のプロジェクトへ転送する必要があった。ログの論理的な所有はアプリ、転送の設定の所在はブランド側という分かれ方をしていた。Cloud Run では各環境のプロジェクトにログが直接集まるため、この分かれ方は無くなり、収集も監視の定義も環境プロジェクトの中で完結する。

従来のモニタリング方針は、クラスタ上のマネージド Prometheus と、収集の対象をクラスタへ宣言する仕組みを前提にしていた。クラスタが無くなったことで、この前提は成り立たない。Cloud Run は要求の数・応答時間・ログの件数を標準のメトリクスとして出す。

## 不採用案

### ログの一致でアラートを出す

ログの内容そのものを条件にして発報する方式。この方式には、ログの保存先・転送の設定・ログを数えるメトリクスの定義がそれぞれ要る。Cloud Logging が標準で出すログ件数のメトリクスを severity で絞れば同じ事象を同じ粒度で捉えられ、これらを一つも定義せずに済むため採用しない。

### dev をアラートの対象から外す

dev では動作確認でわざとエラーを起こすため、通知が増える。しかし対象から外すと dev の障害に気づけず、実際に気づけなかった事例がある。許容する件数を環境ごとに緩める方で対処する。

### 5xx と ERROR ログのどちらか一方だけを監視する

二重に発報する問題は消えるが、片方では取りこぼす。インスタンスが起動できないときに Cloud Run 自身が返す 503 やコンテナの異常終了は 5xx にしか現れない。WebSocket の処理・ゲームの進行・Pub/Sub の受信・ジョブの実行は要求として現れないため、ERROR ログにしか出ない。

### 予算を超えたら使用を自動で止める

請求データが集計に反映されるまで数時間の遅れがあり、超過を検知した時点で止めても防ぎきれない。目的を果たせないため、通知だけを行う。

## 残課題

デプロイの失敗と、稼働できるリビジョンが一本も無い状態は、本 ADR のアラートでは捉えられない。起動に失敗したコンテナは要求を受け取らないので 5xx が出ず、起動を試みる一回あたりの ERROR ログも許容する件数に届かない。dev のデプロイが三週間失敗し続けた事例はこの型に当たるので、別の仕組みが要る。

応答時間の閾値は、コールドスタートを含む実測が無いまま置いている。運用を始めてからの実測で詰める。
