# Overload Party — ルールブック

**「クラウドアーキテクトとして最強のインフラを構築し、ライバル企業のシステムを打ち破れ。」**

---

## 1. ゲームの目的

相手の **Budget（バジェット）** を **0 以下** にすれば勝ち。

Budget はあなたの行動資金であり、同時にライフポイントでもある。
カードの配置・強化・攻撃、すべてに Budget を使う。攻撃で相手のカードを壊すと、相手の Budget が減る。

その他の勝利条件については#10参照。

---

## 2. 準備

### 初期条件

| 項目 | 内容 |
|------|------|
| リポジトリ | **30枚**（同名カードは **3枚** まで。制限カードは **1枚** まで。準制限カードは **2枚** まで） |
| 初期手札 | **5枚** |
| 初期 Budget | **5,000** |
| 初期 DV プール | **0** |

### ゲーム開始時の流れ

ゲーム開始時、以下の手順で初期フィールドを構築する:
1. 各プレイヤーは構築済みの30枚デッキから、以下を「Starting Resource」として選出する:
   - フロントエンド用リソース 1体
   - バックエンド用リソース 1体
2. 両プレイヤーは選出した2体を**同時に公開**する
3. 選出した2体分のデプロイコストを払い、フィールドに配置する
4. 残りの28枚をシャッフルしてリポジトリとする
5. 初期手札5枚をドローする

## 3. フィールドと手札

### フィールド

```
┌──────────┐ ┌──────────┐ ┌──────────┐  ┌──────────┐
│ Frontend 1  │ │ Frontend 2  │ │ Frontend 3  │  │Support 1 │
└──────────┘ └──────────┘ └──────────┘  ├──────────┤
┌──────────┐ ┌──────────┐ ┌──────────┐  │Support 2 │
│  Backend 1  │ │  Backend 2  │ │  Backend 3  │  ├──────────┤
└──────────┘ └──────────┘ └──────────┘  │Support 3 │
  フロントエンド（コンピュート系リソース / Object Storage）/ バックエンド（全タイプ）  └──────────┘
                                         Platform or Reactive（共用 3枠）
┌────────────┐ ┌────────────┐
│ Repository │ │   Trash    │
│ リポジトリ  │ │ トラッシュ   │
└────────────┘ └────────────┘
  山札（ドロー元）  使用済み / 破壊済み
```

| ゾーン | 上限 | 置けるカード |
|-------|------|------------|
| **フロントエンド** | 3体 | コンピュート系リソース、AI/ML系リソース、Object Storage |
| **バックエンド** | 3体 | 全タイプのリソース |
| **サポートゾーン** | 3枚 | プラットフォーム、リアクティブ（共用） |
| **リポジトリ** | — | 山札。ここからドローする |
| **トラッシュ** | — | 破壊されたカード・使用済みカードの置き場 |

- **アタッチメント** はリソースに装備する（枠を消費しない）。

### 手札
毎ターン開始時に **+500 Budget** が自動追加され、リポジトリから1枚ドローして手札に加える。
手札上限は **6枚**。ターン終了時に手札が6枚を超えている場合、6枚になるまで選んで捨てる。
なお、この方法でトラッシュに置かれたカードは「破壊された」とは扱わない。

### 情報の可視性

フィールド上の全てのカードは両プレイヤーに公開情報である。ただし、サポートゾーンに裏向きで伏せられたリアクティブカードのみ、発動するまで非公開となる。

## 4. カードの読み方

### コンピュート系リソース

```
┌────────────────────────────────┐
│ えくぼ        SWS      可用性  1,400 │ ← カード名 / 陣営 / 可用性最大値
│ Compute (R)          スループット    600 │ ← タイプ・区分 / スループット最大値
│┌──────────────────────────────┐│
││                              ││
││                              ││
││         〈 イラスト 〉        ││
││                              ││
││                              ││
│└──────────────────────────────┘│
│維持コスト        150             │
│開発コスト        400            │
│SLAペナルティ     400            │
│                                │
│ 効果: —                        │
└────────────────────────────────┘
```

- 数値は **small (Rank 1)** 基準
- **(R)** = Resizable, **(E)** = Elastic, **(R+E)** = 両方
- Elastic カードは「base→上限」で表記
- カード右上の **可用性** と **スループット** はそのカードの**最大値**。ゲーム中はダメージや効果で変動するため、**現在値**を別途トラッキングする
- **可用性** = 耐久値の最大値。ダメージは永続で蓄積し、現在可用性が 0 以下で破壊
- **スループット** = 攻撃力 兼 Revenue 変換上限の最大値。Elastic 効果などで現在スループットが変動する
- **維持コスト (Maintenance Cost)** = ターン終了時に支払うランニングコスト。Resizable は固定、Elastic は利用量に応じて増加
- **開発コスト** = カードをフィールドに出す / Scale Up するときの Budget
- **SLAペナルティ** = カード破壊時にオーナーの Budget から強制減算
- バックエンド（Backend）はスループットの代わりに **DV Gen**（毎ターン DV 生成量）を持つ

## 5. カードタイプ

### リソース

フィールドに配置する永続カード。フロントエンドとバックエンドに配置できる。

**コンピュート系リソース**

スループット（Throughput）は攻撃力を兼ねる。**バックエンドに置いた Compute のみ**が DV を収益化（DV → Budget 変換）できる。

| サブタイプ | 特徴 | 配置可能ゾーン |
|----------|------|---------------|
| **Compute** | 基本ユニット。バランスのとれた攻撃性能 | Frontend / Backend |
| **Container** | 攻撃を受けるほどスループット上昇。即戦力 | Frontend / Backend |
| **Orchestrator** | 手動成長 + 自動変動の両方。最も柔軟で強力 | Frontend / Backend |
| **Serverless** | 維持コスト 0。攻撃を受けるとスループット上昇 | Frontend / Backend |

**AI/ML系リソース**

機械学習・深層学習基盤。フロントエンドにもバックエンドにも配置できるが、独自の強力な効果を持つ。

| サブタイプ | 特徴 | 配置可能ゾーン |
|----------|------|---------------|
| **AI/ML** | スループット最高だが可用性は低め。独自の条件でステータスが強化される | Frontend / Backend |

**DB系リソース（主な DV 生成源）**

| サブタイプ | 特徴 | 配置可能ゾーン |
|----------|------|---------------|
| **Database** | 主力の DV 源。DV Gen が高いが可用性は低め | Backend のみ |
| **NoSQL** | DV 消費に連動して DV Gen が自動上昇 | Backend のみ |
| **Cache DB** | デプロイ時にボーナス効果を持つ補助 DB | Backend のみ |

**オブジェクトストレージ**

| サブタイプ | 特徴 | 配置可能ゾーン |
|----------|------|---------------|
| **Object Storage** | 可用性高め。**フロントエンドに置いた場合は静的ホスティング用途となり、データ生成はできない** | Frontend / Backend |

### プラットフォーム

Support Zone に**表向き**で配置する持続効果カード。全フロントエンドのスループット上昇、Scale Up コスト軽減、セキュリティ機能など、置いている限り恩恵を受け続ける。

### アタッチメント

Resource に装備する強化カード。Load Balancer（攻撃対象から保護）、Auto Scaler（Scale Up 時ボーナス）などがある。

### ストラテジー

手札から使用する即時効果カード。ドロー、サーチ、Budget 回復などの支援効果がある。
使用後はトラッシュへ送られる。

### インシデント

相手のフィールドやリソースに対して直接干渉する使い切りカード。

**DV奪取について:**
「相手のDVを奪う」効果は、相手の **DVプール** から指定された数値を減らし、自分のDVプールに加算する処理を指す。
相手のDVプールが指定値未満の場合は、ある分だけを奪う（マイナスにはならない）。

手札から使用し、相手を妨害する攻撃カード。Main Phase に **1ターン1枚** まで使用可能。Battle Phase の攻撃とは別枠なので、バトルに加えて追加ダメージを与えられる。一部の Incident は Security (Block) Platform で無効化できる。
使用後はトラッシュへ送られる。

### リアクティブ

Support Zone に**裏向き**で伏せる反応型カード。**条件を満たした瞬間に自動的に発動する。プレイヤーの宣言は不要。**

- **攻撃を受けた時**: サポートゾーンのリアクティブが全て自動的に走査・発動される（DeployOrder 順）
- **リソースが破壊された時**: 破壊トリガーを持つカードが自動発動する
- **カード効果の誘発時**: 攻撃・効果に連動して自動発動する

> クラウドのオートスケールやアラート通知のように、**条件を設定しておけばシステムが自動で反応する**のがこのゲームの設計思想。一度サポートゾーンに伏せれば、プレイヤーが意識しなくても機能し続ける。

プラットフォームとサポートゾーンを共有するため、持続バフと自動防御のどちらに枠を割くかが戦略の鍵。

## 6. カード区分 — Resizable と Elastic

Resource カードには **Resizable (R)** と **Elastic (E)** の2つの属性がある。これらはカードごとに個別に設定されており、カードのタイプ欄に記載される。

| 区分 | 意味 |
|------|------|
| **(R)** | Resizable — 手動でランクアップ可能 |
| **(E)** | Elastic — 負荷に連動して自動変動 |
| **(R+E)** | 両方の属性を持つ |
| **—** | どちらでもない（固定スペック） |

これらの属性は排反せず、**サブタイプに依存しない**。同じ Database でも、手動スケーリングのサービス（RDS）は (R)、自律型サービス（Autonomous DB）は (E) と、元のクラウドサービスの実際のスケーリングモデルに基づいて個別に設定される。

---

### Resizable（リサイザブル）— 手動ランクアップ

**(R) または (R+E) のカードが対象。**

3段階: **small → medium → large**

| ランク | 全パラメータ倍率 |
|-------|---------------|
| small | ×1（基本値そのまま） |
| medium | ×2 |
| large | ×3 |

スループット, 可用性, DV Gen, SLAペナルティすべてが倍率に従ってスケールする。
Scale Up のコストは、カードの **開発コスト** と同額。
**カード効果による加算値は Rank 倍率の影響を受けない（フラット加算）。**

> 例: えくぼ (スループット 700, 可用性 1,400)
> small: スループット 700, 可用性 1,400 → medium: スループット 1,400, 可用性 2,800 → large: スループット 2,100, 可用性 4,200
>
> 例: Smile Aurora (DV 500) + Aurora Cluster (+200/DB)
> large 時: 500×3 + 200 = 1,700（+200 は倍率外）

**ダメージは保持される。** 可用性 1,400 で 600 ダメージを受けた状態（残可用性 800）で Scale Up すると、
可用性上限は 2,800 になるが現在可用性は **2,200**（600 ダメージが残る）。

### Instance Family（Resizable のみ）

最初の Scale Up 時に方向性を選ぶ（以降変更不可）:

| 系統 | スループット / DV Gen | 可用性 |
|------|-------------|-----|
| **M系（バランス）** | 標準 | 標準 |
| **C系（攻撃特化）** | **×1.5** | **×0.75** |
| **R系（耐久特化）** | **×0.75** | **×1.5** |

---

### Elastic（エラスティック）— 負荷連動の自動変動

**(E) または (R+E) のカードが対象。**

Elastic カードのスペックは **「base → 上限」** で表記される（例: スループット 600→1,200）。
通常時は base 値で動作し、特定の条件によって自動的にスペックが変動する。

#### フロントエンド Elastic

- 攻撃を受けた**ダメージの分だけ**、次の自分のターンのスループットが上昇（上限値まで累積）
- 自分のターンの終了時に、スループットが base に戻る
- 負荷（攻撃）に応じてスループットが自動的にスケールアップし、負荷がなくなると縮退する

> 例: Container (スループット 600→1,200) がスループット 600 の攻撃を受けた →
> 次ターンスループット +600 → 上限 1,200 でキャップ。
> 次ターンの終了時に、スループット 600 に戻る。

#### バックエンド Elastic

- Revenue Phase で消費された DV の分だけ、次ターンの DV Gen が上昇（上限まで）
- 次の自分のターンの終了時に、DV Gen が base に戻る 

> 例: NoSQL (DV Gen 400→800) — Revenue で DV 400 が消費されると、次ターンは DV Gen +400。
> 次ターンの終了時に、DV Gen 400 に戻る。

#### Resizable + Elastic

R+E のカードは両方の属性を持つ。
**Elastic 加算分（上限 - base）は Rank に依らず固定。** Scale Up しても Elastic 幅は変わらない。

> 例: Orchestrator (スループット 600→1,000) — Elastic 幅は常に +400
> small: 600～1,000 / medium: 1,200～1,600 / large: 1,800～2,200

## 7. Budget と DV

### Budget — 行動資金 兼 ライフポイント

Budget はあらゆるアクションの燃料であり、同時にライフポイントである。

**増やす方法:**
- 収益化フェーズで Compute が DV を Budget に変換する（メイン収入源）
- ストラテジーカードの効果

**使う場面:**
- デプロイ、スケールアップ、攻撃、インシデント / ストラテジーの使用

**強制減少:**
- 自分のリソースが破壊された時 →SLAペナルティ分の Budget を失う

### DV（Data Value）— 中間データ資源

バックエンドの DB/Object Storage が各ターンのエンドフェーズに自動生成するデータ資源。DV プールに蓄積され、フロントエンドの Compute が Revenue Phase で Budget に変換する。
DV プールに上限はない。

### 収益化

**バックエンドに配置した コンピュート系リソース**が、DV プールから DV を消費して **Budget** に変換する。
フロントエンドの Compute は収益化できない。

- 変換レート: **1 DV = 1 Budget**
- 各カードの変換上限 = その **スループット** の値
- DV プールが足りなければ、ある分だけ変換
- **手動処理**: プレイヤーが任意のバックエンド Compute カードを選び、DV を割り当てる。割り当ての順序と量はプレイヤーが自由に決定できる

> 例: バックエンドに えくぼ (スループット 700) + ラム (スループット 500)。DV プールに 1,200 あれば →
> プレイヤーは えくぼ に 700 DV、ラム に 500 DV を割り当てて、合計 Budget +1,200。DV 残り 0。
>
> もし DV プールが 400 しかなければ → プレイヤーは えくぼ に 400 DV を割り当てて Budget +400（ラムには割り当てない）、または えくぼ に 200、ラム に 200 を割り当てる等、自由に配分できる。

### リソースフロー

```
DB/Object Storage（Backend） → DV 生成 → [DV プール] → Backend Compute が変換 → Budget 回復
                                                                           ↓
                                                  Deploy / Scale / Attack / Incident 等に消費
                                                                           ↓
                                                  Resource 破壊 →SLAペナルティで Budget 減少
```

## 8. バトルのルール

### 基本ルール

**コンピュート系リソース**カードは **1ターンに1回** 攻撃できる（フロントエンド・バックエンドどちらに置いていても同様）。
**Object Storage をフロントエンドに置いた場合、そのカードは攻撃できない。**

1. 攻撃するカードを選ぶ
2. 相手の**フロントエンド**カード 1体を選んで攻撃
3. ダメージ = 自分の **スループット**
4. 相手の **可用性** からダメージを引く
5. 可用性が 0 以下 → **破壊**。相手の Budget から **SLAペナルティ** を引く

**重要なルール:**
- **攻撃にコストはかからない**（維持コストはターン終了時に別途徴収）
- **デプロイしたターンから攻撃可能**（召喚酔いなし）
- Cold Start はこのルールの例外ではなく、個別カード効果として記載がある場合のみ適用される
- **反撃なし:** 攻撃された側は自動反撃しない
- オーバーキル分のダメージは消失
- **可用性は自動回復しない。** Strategy / Attachment / Platform 効果でのみ回復可能
- 複数の Resource が同時に破壊された場合、**ターンプレイヤーのカードから順に**処理する。
 SLAペナルティは破壊されたカードごとに即座に適用される。

### バックエンドへの攻撃

バックエンドのカードは**通常は攻撃対象にできない**（コンピュート系、AI/ML系、DB系、オブジェクトストレージを問わず）。以下の場合のみ攻撃可能:

| 条件 | 説明 |
|------|------|
| **フロントエンドが 0体** | 相手のフロントエンドが全滅していれば、バックエンドを直接攻撃できる |
| **Incident** | 一部のインシデントはバックエンドを直接対象にできる |

> フロントエンドを全部倒す → バックエンドを直接攻撃できる → DV 生成が止まり収益化もできなくなる。
> **フロントエンドは「バックエンドを守る壁」。フロントエンドを崩すことが攻略の基本。**

## 9. ゲームの流れ

### Phase 1: ドローフェーズ

リポジトリから **1枚** 引き、手札に加える。

### Phase 2: メインフェーズ

**Budget** を消費して、以下のアクションを**好きな順序・回数**で実行できる:

| アクション | 内容 | コスト |
|-----------|------|--------|
| **デプロイ** | 手札からカードをフィールドに出す | 開発コスト（Budget） |
| **スケールアップ** | Resizable カードのランクを上げる | カードの開発コスト |
| **アタッチ** | Attachment を Resource に装備 | **無料** |
| **ストラテジー** | Strategy カードを使用 | カードに記載 |
| **インシデント** | 相手を妨害（**1ターン1枚**） | カードに記載 |
| **リアクティブ配置** | Reactive を Support Zone に伏せる | **無料** |
| **収益化** | DV を Budget に変換する | **無料** |

**DV生成は行われない（エンドフェーズに移動）。**

### Phase 3: バトルフェーズ

バトルを行うことができる。バトルのルールについては#8参照。

### Phase 4: エンドフェーズ

ターン終了処理を行う。
1. **維持コスト徴収:** フィールド上の全リソースの維持コストを Budget から差し引く
   - Resizable: 維持コスト × ランク乗数（small×1, medium×2, large×3）
   - Elastic: 維持コスト × ランク乗数 × (実効値 / ベース値)。利用量が増えるほどコスト増加
2. 一時的な効果（「このターン中」など）の終了
3. **DV 生成:** バックエンドの各カードが自動的に DV を生成し、DV プールに加算する
4. 手札調整（上限 6枚になるように捨てる）
5. 相手にターンを渡す

### 先攻プレイヤーの制限

先攻の第1ターンは **Draw + Main Phase + End Phase のみ**。
Revenue Phase（メインフェーズ内での収益化）、Battle Phase をスキップする。
（DV生成はエンドフェーズに行われるため、先攻1ターン目終了時にも生成される。次の自ターンまでプールで保持する必要がある）

## 10. ゲームの終了

以下のいずれかが起きたらゲーム終了:

1. **Budget 0 以下** — そのプレイヤーが**敗北**（破産）
2. **フィールドの Resource 0 体** — そのプレイヤーが**敗北**（システムダウン）
3. **リポジトリ 0枚** — そのプレイヤーが**敗北**（リポジトリアウト）

> **システムダウン:** フロントエンド・バックエンドを問わず、フィールド上の Resource が全て失われた時点で即敗北。
> 手札にカードがあっても間に合わない——インフラが完全停止した瞬間にゲームオーバー。

## 11. その他のルール

### 端数処理

倍率計算の結果が整数にならない場合、**1 の位で切り捨てる**（1 未満切り捨て）。

> 例: 可用性 1,350 を半分 → 675（端数なし）
> 例: 可用性 1,350 × 0.75 → 1,012.5 → **1,012**

### 効果の回数制限

カード効果に回数制限の記載がない場合、**回数無制限**で使用できる。

回数制限がある効果は「1ゲーム中に1回」「1ターン中に1回」等、効果テキストの末尾に明記される。

### コスト軽減の下限

カード効果によってコストが軽減される場合、**コストは 0 未満にはならない**。

> 例: 開発コスト 300 のカードに「開発コスト -200」と「開発コスト -200」の効果が両方適用される場合 →
> 300 - 200 - 200 = -100 ではなく、**0** となる。

## 12. 詳細ルール

### チェーンシステム

このゲームでは、遊戯王のチェーンシステムに準拠したルールを採用する。

**チェーンの基本:**
- 行動やカード効果に対して、リソースの誘発効果やリアクティブカードが**自動的にチェーンに積まれる**
- チェーンは「後入れ先出し（Last In, First Out）」で解決される
- **重要**: リアクティブカードに対して、別のリアクティブカードをチェーンすることは**できない**（カウンター罠相当のカードは存在しない）
- **最大チェーン数**: **3**（行動 → リソース効果 → リアクティブ）

**チェーンの例:**
1. プレイヤーAが「DDoS Attack」（Incident）を使用
2. プレイヤーBのサポートゾーンに伏せてあった「Rate Limiter」（Reactive）が**自動発動**してチェーンに積まれる
3. プレイヤーBのリソース（例: 攻撃時効果を持つカード）の誘発効果も**自動的に**チェーンに積まれる
4. チェーン解決（LIFO）: リソース誘発効果 → Rate Limiter → DDoS Attack の順で解決
5. リアクティブに対して、さらにリアクティブをチェーンすることはできない

### アタッチメントのルール

**装備スロット:**
- 各 Resource は **アタッチメントスロットを 2 つ** 持つ。1体の Resource に装備できる Attachment は**最大 2枚**まで
- スロットが埋まっている場合、新たに装備することはできない（既存の Attachment を外すことはできない。装備先の破壊・バウンス等でのみ外れる）

**装備と破壊:**
- Attachment は Resource に装備コスト **0（無料）** で装備できる
- 同じ Attachment を複数装備することは**可能**。ただし、カードに「同名カードは1枚まで」等の記載がある場合はそれに従う
- 装備先の Resource が破壊されるか、フィールドを離れた場合、装備されていた全ての Attachment は**トラッシュに送られる**
- この方法でトラッシュに送られた Attachment は「**破壊された**」として扱う

### 効果の持続期間

効果テキストに記載された持続期間の定義:

| 表記 | 意味 |
|------|------|
| **このターン** | 現在の自分のターン終了まで |
| **次のターン終了まで** | 次の自分のターン終了まで |
| **2ターンの間** | 次の自分のターン終了まで（「次のターン終了まで」と同義） |

> 例: 「このターン、スループットを +200 する」→ 現在の自分のターンのみ有効
> 例: 「次のターン終了まで、可用性を +500 する」→ 次の自分のターン終了まで有効

### 効果の適用タイミング

**常時効果:**
- 全ての継続効果は、フィールドの状態に基づいて**常時再計算**される
- 条件を満たした瞬間に効果が適用され、条件を満たさなくなった瞬間に効果が消失する

> 例: 「場に SWS カード 3枚以上でスループット +200」→ SWS カードが 3枚になった瞬間にスループット +200、2枚以下になった瞬間に効果消失

### サーチ効果の失敗

**対象が見つからない場合:**
- サーチ効果で対象が見つからない場合でも、**コストは支払われる**
- 例: Cloud Engineer / Cloud Architect で2枚ドローし、両方とも Miracle カードだった場合 → 両方ともトラッシュに送られる（Miracle デッキには採用されない想定）

### バウンス（手札に戻す）

**カードが手札に戻った場合:**
- Resource が手札に戻った場合、全ての変更がリセットされる:
  - Rank は small に戻る
  - 全てのダメージが除去される
  - Instance Family の選択がリセットされる
  - Elastic の値が base に戻る
  - 装備されていた Attachment は全てトラッシュに送られる（破壊扱い）

### ターンタイマー

遊戯王マスターデュエルの仕様に準拠したターンタイマーを採用する:

- 各プレイヤーは**タイムバンク**を持つ（例: 8分）
- 各アクションには短いタイマーがある（例: 30秒）
- 自分のターン中、タイムバンクが減少する
- タイムバンクが 0 になったプレイヤーは**敗北**

> 詳細な時間設定は実装時に調整可能
