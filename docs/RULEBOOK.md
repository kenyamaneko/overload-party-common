# Overload Party — ルールブック

**「クラウドアーキテクトとして最強のインフラを構築し、ライバル企業のシステムを打ち破れ。」**

---

## 1. ゲームの目的

相手の **Budget（バジェット）** を **0 以下** にすれば勝ち。

Budget はあなたの行動資金であり、同時にライフポイントでもある。
カードの配置・強化・攻撃、すべてに Budget を使う。攻撃で相手のカードを壊すと、相手の Budget が減る。

その他の勝利条件については#10参照。

---

## 2. 準備

### 初期条件

| 項目 | 内容 |
|------|------|
| リポジトリ | **30枚**（同名カードは **3枚** まで。制限カードは **1枚** まで。準制限カードは **2枚** まで） |
| 初期手札 | **5枚** |
| 初期 Budget | **5,000** |
| 初期 Insight プール | **0** |

### ゲーム開始時の流れ

1. 構築済みの 30 枚デッキをシャッフルしてリポジトリとする
2. 初期手札 5 枚をドローする
3. T1 開始（フィールドは空の状態でゲーム開始）

> **スタートアップが初日から K8s を使うことはない。** 手札から最初のリソースを選んでデプロイするところからゲームが始まる。Serverless なら即座に稼働できるが、Orchestrator は構築に時間がかかる——デッキ構築の段階から序盤戦略を組み立てよう。

## 3. フィールドと手札

### フィールド

```
┌──────────┐ ┌──────────┐ ┌──────────┐  ┌──────────┐
│ Frontend 1  │ │ Frontend 2  │ │ Frontend 3  │  │Support 1 │
└──────────┘ └──────────┘ └──────────┘  ├──────────┤
┌──────────┐ ┌──────────┐ ┌──────────┐  │Support 2 │
│  Backend 1  │ │  Backend 2  │ │  Backend 3  │  ├──────────┤
└──────────┘ └──────────┘ └──────────┘  │Support 3 │
  フロントエンド（コンピュート系リソース / Object Storage）/ バックエンド（全タイプ）  └──────────┘
                                         Platform or Reactive（共用 3枠）
┌────────────┐ ┌────────────┐
│ Repository │ │   Trash    │
│ リポジトリ  │ │ トラッシュ   │
└────────────┘ └────────────┘
  山札（ドロー元）  使用済み / 破壊済み
```

| ゾーン | 上限 | 置けるカード |
|-------|------|------------|
| **フロントエンド** | 3体 | コンピュート系リソース、AI/ML系リソース、Object Storage |
| **バックエンド** | 3体 | 全タイプのリソース |
| **サポートゾーン** | 3枚 | プラットフォーム、リアクティブ（共用） |
| **リポジトリ** | — | 山札。ここからドローする |
| **トラッシュ** | — | 破壊されたカード・使用済みカードの置き場 |

- **アタッチメント** はリソースに装備する（枠を消費しない）。

### 手札
リポジトリから1枚ドローして手札に加える。
手札上限は **6枚**。ターン終了時に手札が6枚を超えている場合、6枚になるまで選んで捨てる。
なお、この方法でトラッシュに置かれたカードは「破壊された」とは扱わない。

### 裏向きカード（デプロイ中）

リソースカードおよび Platform は、デプロイ時に**裏向き**でフィールドに配置される（デプロイターンが 0 のカードは即座に表向きになる）。裏向きカードは以下のルールに従う:

| 側面 | ルール |
|------|--------|
| フィールド存在 | **いないものとみなす**（攻撃対象外、戦力として計算しない） |
| 攻撃 | **攻撃対象にできない。攻撃もできない** |
| 攻撃の貫通 | Frontend に裏向きしかいない場合、Backend を直接攻撃可能 |
| System-Down 判定 | カウントしない（表向きリソースが 0 体 = System-Down） |
| メンテナンスコスト | **不要**（稼働していない） |
| Yield 生成 | **しない** |
| パッシブ / Platform 効果 | **適用しない・受けない** |
| スロット占有 | **する**（同じスロットに別カードは配置不可） |

> 裏向きカードは「まだ構築中のインフラ」を表す。稼働していないのでコストもかからないが、戦力としても機能しない。

### 情報の可視性

フィールド上の全てのカードは両プレイヤーに公開情報である。デプロイ中の裏向きカードも**カード名は公開**される（何をデプロイしているかは相手に見える）。ただし、サポートゾーンに裏向きで伏せられたリアクティブカードのみ、発動するまで非公開となる。

## 4. カードの読み方

### カード名の構成

リソースカードの名前は以下の要素で構成される:

| 要素 | 説明 | 例 |
|------|------|-----|
| **カード名** | キャラクター/エンティティの固有名 | ソラ、えくぼ、アリゲーテナ |
| **リソースラベル** | リソースの技術分類（表示用の技術名） | VM、Container、RDB、NoSQL |
| **陣営** | 所属陣営（別フィールドで管理） | SHE、天気使い、しゅがーらぼ、調律部 |

表示例: カード名「ソラ」、サブラベル「天気使い VM」

サポートカード（Platform / Attachment / Strategy / Reactive / Incident）にはリソースラベルはない。

### コンピュート系リソース

```
┌────────────────────────────────┐
│ えくぼ         SHE       可用性  1,400 │ ← カード名 / 陣営 / 可用性最大値
│ Compute (R)           スループット    600 │ ← リソースラベル・区分 / スループット最大値
│┌──────────────────────────────┐│
││                              ││
││                              ││
││         〈 イラスト 〉        ││
││                              ││
││                              ││
│└──────────────────────────────┘│
│維持コスト        150             │
│デプロイターン     1              │
│SLAペナルティ     400            │
│                                │
│ 効果: —                        │
└────────────────────────────────┘
```

- 数値は **small (Rank 1)** 基準
- **(R)** = Resizable, **(E)** = Elastic, **(R+E)** = 両方
- Elastic カードは base 値で表記（ElasticBonus により実効値が増加）
- カード右上の **可用性** と **スループット** はそのカードの**最大値**。ゲーム中はダメージや効果で変動するため、**現在値**を別途トラッキングする
- **可用性** = 耐久値の最大値。ダメージは永続で蓄積し、現在可用性が 0 以下で破壊
- **スループット** = 攻撃力 兼 収益化の変換上限の最大値。ElasticBonus やカード効果で現在スループットが変動する
- **維持コスト (Maintenance Cost)** = ターン終了時に支払うランニングコスト。Non-Elastic は固定（× ランク倍率）、Elastic は固有ステータスの `free_tier` 超過分 × `cost_per_request` で増加（`free_tier` 以下なら無料）
- **デプロイターン (Deploy Turns)** = デプロイしてから稼働するまでに必要なターン数。0 なら即座に稼働、1 なら次の自分のターンに稼働、2 ならその次。カードタイプごとに異なり、技術の構築難易度を表す
- **SLAペナルティ** = カード破壊時にオーナーの Budget から強制減算
- バックエンド（Backend）はスループットの代わりに **Yield**（毎ターン Insight 生成量）を持つ

## 5. カードタイプ

### リソース

フィールドに配置する永続カード。フロントエンドとバックエンドに配置できる。

**コンピュート系リソース**

スループット（Throughput）は攻撃力を兼ねる。**バックエンドに置いた Compute のみ**が Insight を収益化（Insight → Budget 変換）できる。

| サブタイプ | デプロイターン | 特徴 | 配置可能ゾーン |
|----------|:---:|------|---------------|
| **Serverless** | **0** | 維持コスト 0。即座に稼働。Elastic により自動スケーリング | Frontend / Backend |
| **Container** | **0** | マネージドコンテナ。Elastic により自動スケーリング | Frontend / Backend |
| **Compute** | **1** | 基本ユニット。バランスのとれた攻撃性能 | Frontend / Backend |
| **Orchestrator** | **2** | 手動成長 + 自動変動の両方。構築に時間がかかるが最も柔軟で強力 | Frontend / Backend |

**AI/ML系リソース**

機械学習・深層学習基盤。フロントエンドにもバックエンドにも配置できるが、独自の強力な効果を持つ。

| サブタイプ | デプロイターン | 特徴 | 配置可能ゾーン |
|----------|:---:|------|---------------|
| **AI/ML** | **2** | スループット最高だが可用性は低め。MLパイプライン構築に時間がかかる | Frontend / Backend |

**DB系リソース（主な Insight 生成源）**

| サブタイプ | デプロイターン | 特徴 | 配置可能ゾーン |
|----------|:---:|------|---------------|
| **Database** | **0〜1** | 主力の Insight 源。Yield が高いが可用性は低め。NoSQL 系カードも Database に含まれる（`resource_label` で表示上区別） | Backend のみ |
| **Cache DB** | **0** | マネージドキャッシュ。デプロイ時にボーナス効果を持つ補助 DB | Backend のみ |

**オブジェクトストレージ**

| サブタイプ | デプロイターン | 特徴 | 配置可能ゾーン |
|----------|:---:|------|---------------|
| **Object Storage** | **0** | 可用性高め。即座に稼働。**フロントエンドに置いた場合は静的ホスティング用途となり、Insight生成はできない** | Frontend / Backend |

> **デプロイターンと技術選定:** Serverless（0ターン）や マネージド Database（0ターン）はすぐに使える反面、ステータスは控えめ。Orchestrator（2ターン）や AI/ML（2ターン）は稼働まで時間がかかるが、完成すれば強力。現実のクラウド技術選定と同じトレードオフがゲームに反映されている。

### プラットフォーム

Support Zone に配置する持続効果カード（**デプロイターン: 2**）。CI/CD パイプライン等の構築に時間がかかるが、稼働すればスループット上昇、マイグレーション時間短縮、セキュリティ機能など、置いている限り恩恵を受け続ける。

### アタッチメント

Resource に装備する強化カード。Load Balancer（攻撃対象から保護）、Auto Scaler（Scale Up 時ボーナス）などがある。

### ストラテジー

手札から使用する即時効果カード。ドロー、サーチ、Budget 回復などの支援効果がある。
使用後はトラッシュへ送られる。

### インシデント

相手のフィールドやリソースに対して直接干渉する使い切りカード。

**インサイト吸収について:**
「相手のInsightを吸収する」効果は、相手の **Insightプール** から指定された数値を減らし、自分のInsightプールに加算する処理を指す。
相手のInsightプールが指定値未満の場合は、ある分だけを吸収する（マイナスにはならない）。

手札から使用し、相手を妨害する攻撃カード。Main Phase に **1ターン1枚** まで使用可能。Battle Phase の攻撃とは別枠なので、バトルに加えて追加ダメージを与えられる。一部の Incident は Security (Block) Platform で無効化できる。
**先攻 T1 では使用不可**（先攻1キル防止。詳しくは#9参照）。
使用後はトラッシュへ送られる。

### リアクティブ

Support Zone に**裏向き**で伏せる反応型カード。**条件を満たした瞬間に自動的に発動する。プレイヤーの宣言は不要。**

- **攻撃を受けた時 / リソースがデプロイされた時**: サポートゾーンのリアクティブのうち、**最も早くセットされたもの1つだけ**が自動発動する（DeployOrder が最小のもの）。複数のリアクティブがセットされていても、1アクションにつき発動するのは1枚のみ
- **リソースが破壊された時**: 破壊トリガーを持つカードが自動発動する

> クラウドのオートスケールやアラート通知のように、**条件を設定しておけばシステムが自動で反応する**のがこのゲームの設計思想。一度サポートゾーンに伏せれば、プレイヤーが意識しなくても機能し続ける。

プラットフォームとサポートゾーンを共有するため、持続バフと自動防御のどちらに枠を割くかが戦略の鍵。

## 6. カード区分 — Resizable と Elastic

Resource カードには **Resizable (R)** と **Elastic (E)** の2つの属性がある。これらはカードごとに個別に設定されており、カードのタイプ欄に記載される。

| 区分 | 意味 |
|------|------|
| **(R)** | Resizable — 手動でランクアップ可能 |
| **(E)** | Elastic — トリガーに応じて自動スケーリング（永続累積） |
| **(R+E)** | 両方の属性を持つ |
| **—** | どちらでもない（固定スペック） |

これらの属性は排反せず、**サブタイプに依存しない**。同じ Database でも、手動スケーリングのサービス（RDS）は (R)、自律型サービス（Autonomous DB）は (E) と、元のクラウドサービスの実際のスケーリングモデルに基づいて個別に設定される。Elastic カードは `free_tier` 以下なら維持コスト無料（フリーティアモデル）だが、自動スケーリングで実効値が `free_tier` を超えると `cost_per_request` に比例してコストが増加する。Serverless カード（`cost_per_request=0`）は常に MC=0 となる。

---

### Resizable（リサイザブル）— 手動ランクアップ

**(R) または (R+E) のカードが対象。**

3段階: **small → medium → large**

| ランク | 全パラメータ倍率 |
|-------|---------------|
| small | ×1（基本値そのまま） |
| medium | ×2 |
| large | ×3 |

スループット, 可用性, Yield, SLAペナルティすべてが倍率に従ってスケールする。
**Scale Up に Budget コストはかからない。** ただし、メンテナンスコストもランク倍率に従って増加する（small ×1 → medium ×2 → large ×3）。スケールアップ自体は無料だが、ランニングコストが増えるのが実態に即している。
**カード効果による加算値は Rank 倍率の影響を受けない（フラット加算）。**

> 例: えくぼ (スループット 700, 可用性 1,400)
> small: スループット 700, 可用性 1,400 → medium: スループット 1,400, 可用性 2,800 → large: スループット 2,100, 可用性 4,200
>
> 例: Smile Aurora (Yield 500) + Aurora Cluster (+200/DB)
> large 時: 500×3 + 200 = 1,700（+200 は倍率外）

**ダメージは保持される。** 可用性 1,400 で 600 ダメージを受けた状態（残可用性 800）で Scale Up すると、
可用性上限は 2,800 になるが現在可用性は **2,200**（600 ダメージが残る）。

### Instance Family（Resizable のみ）

（フィールド追加予定）最初の Scale Up 時に方向性を選ぶ（以降変更不可）:

| 系統 | スループット / Yield | 可用性 |
|------|-------------|-----|
| **M系（バランス）** | 標準 | 標準 |
| **C系（攻撃特化）** | **×1.3** | **×0.7** |
| **R系（耐久特化）** | **×0.7** | **×1.3** |

---

### Elastic（エラスティック）— 自動スケーリング

**(E) または (R+E) のカードが対象。**

Elastic カードは、特定のトリガーに応じて **スループット（TP）または Yield が自動的に増加**する。増加分は **ElasticBonus** として**永続的に蓄積**される（ターン終了でリセットされない）。

各 Elastic カードには以下のパラメータが定義されている:

| パラメータ | 説明 |
|-----------|------|
| **`elastic_increment`** | トリガー1回あたりの ElasticBonus 加算量 |
| **`free_tier`** | MC 無料枠の閾値 **かつ** ln 対数変換のスケール係数。**Rank でスケールしない（固定値）** |
| **`cost_per_request`** | `free_tier` 超過分に対する MC レート（1/100 単位）。0 なら常に MC=0（Serverless モデル） |

#### ElasticBonus の蓄積と対数逓減

ElasticBonus は**上限なし**で線形に蓄積し続ける（トリガーごとに `+elastic_increment`）。ただし、実効値には**対数逓減（diminishing returns）**が適用される:

```
effectiveElasticBonus = free_tier × ln(1 + ElasticBonus / free_tier)
```

- 序盤（ElasticBonus が小さい時）: ほぼ線形に成長
- 中盤以降: 対数カーブで逓減し、伸びが鈍化
- 上限は存在しないが、実質的に収束していく

#### Elastic カードのメンテナンスコスト（MC）

Elastic カードの MC は、**固有ステータス**（intrinsicStat）が `free_tier` を超えた分に対して課金される:

```
intrinsicStat = base × rank × family + effectiveElasticBonus
MC = max(0, intrinsicStat - free_tier) × cost_per_request / 100
```

- `intrinsicStat` にはカード本体の数値のみが含まれる（Platform / パッシブ / アタッチメント / 一時的効果は**除外**）
- `free_tier` は**固定値**（Rank でスケールしない）。したがって **Scale Up すると即座に MC が増加**する
- `cost_per_request = 0` のカード（Serverless 等）は常に MC = 0

#### 数値例: Container (base TP=500, increment=100, free_tier=500, cost_per_request=10)

| トリガー回数 | Raw Bonus | Effective Bonus | 実効 TP | MC |
|:---:|---:|---:|---:|---:|
| 0 | 0 | 0 | 500 | 0 |
| 1 | 100 | 91 | 591 | 9 |
| 5 | 500 | 346 | 846 | 34 |
| 10 | 1,000 | 549 | 1,049 | 54 |
| 20 | 2,000 | 804 | 1,304 | 80 |

> free_tier=500 がちょうど base TP と一致するため、base 状態では MC=0（フリーティア）。
> 自動スケーリングが進むほど TP は伸びるが、対数逓減により「青天井」にはならない。
> MC は実効 TP の `free_tier` 超過分に `cost_per_request/100` を掛けた値。

#### トリガー条件（配置ゾーン × カードタイプで決定）

| 配置 | カードタイプ | 増加対象 | トリガー |
|------|------------|---------|---------|
| **フロントエンド** | Compute / AI/ML | **TP** | 攻撃を受けて生存した時 |
| **バックエンド** | Compute / AI/ML | **TP** | 収益化（distribute_yield）に使用された時 |
| **バックエンド** | Database / Data | **Yield** | エンドフェーズの Yield 生成時（毎ターン自動） |

> 例: Container (TP 500, elastic_increment 100, free_tier 500) がフロントエンドで攻撃を受けて生存 →
> ElasticBonus +100（Raw）。effectiveElasticBonus = 500 × ln(1 + 100/500) ≈ 91。実効 TP = 591。
> 5回生存後 → ElasticBonus 500（Raw）、effective ≈ 346。実効 TP = 846。上限なしだが逓減する。

> 例: Database/NoSQL (Yield 400, elastic_increment 100) がバックエンドで稼働中 →
> エンドフェーズの Yield 生成ごとに ElasticBonus +100 が蓄積。
> 数ターン後には Yield が大幅に増加し、Insight 生成量が飛躍的に伸びる（ただし対数逓減あり）。

#### 実効値の計算順序

effectiveElasticBonus は**他のボーナスよりも先に**適用される:

1. ベーススタット（カード定義値）
2. ランク倍率（Resizable の場合）
3. Instance Family 修正（該当する場合）
4. **effectiveElasticBonus（永続・累積・対数逓減済み）**
5. Platform カード効果
6. パッシブ効果
7. アタッチメント効果
8. 一時的効果

> MC 計算に使う `intrinsicStat` はステップ 1〜4 の合計。ステップ 5〜8 は MC に影響しない。

#### Resizable + Elastic

R+E のカードは両方の属性を持つ。
effectiveElasticBonus は Rank 倍率の影響を受けず**フラット加算**される。
ただし `free_tier` は固定値のため、Scale Up すると `intrinsicStat` が `free_tier` を大きく超え、MC が増加する。

> 例: Orchestrator (TP 600, elastic_increment 100, free_tier 600, cost_per_request 10, R+E) が medium (×2) の場合:
> ベース TP = 600 × 2 = 1,200 → effectiveElasticBonus 300 蓄積時 → 実効 TP = 1,200 + 300 = 1,500
> intrinsicStat = 1,500、MC = max(0, 1500 - 600) × 10 / 100 = **90**

#### ElasticBonus のリセット

ElasticBonus は以下の場合にリセットされる:
- カードが**破壊**された場合
- カードが**手札に戻された**（バウンス）場合
- 通常のターン経過では**リセットされない**（永続）

---

## 7. Budget と Insight

### Budget — ライフポイント 兼 運営資金

Budget はライフポイントであり、ランニングコストの支払い原資でもある。

**増やす方法:**
- メインフェーズの収益化で Compute が Insight を Budget に変換する（メイン収入源）
- ストラテジーカードの効果

**減る場面:**
- 毎ターンのメンテナンスコスト（リソースの維持費）
- 自分のリソースが破壊された時の SLA ペナルティ
- 一部のストラテジー / インシデントのコスト

> デプロイとスケールアップに Budget はかからない。クラウドでは「構築にかかるのは時間（デプロイターン）であり、コストはランニング（メンテナンスコスト）で発生する」——この現実を反映している。

### Insight — 中間データ資源

バックエンドの DB/Object Storage が各ターンのエンドフェーズに自動生成するデータ資源。Insightプールに蓄積され、バックエンドの Compute がメインフェーズの収益化（distribute_yield アクション）で Budget に変換する。
Insightプールに上限はない。

### 収益化

**バックエンドに配置した コンピュート系リソース**が、Insightプールから Insight を消費して **Budget** に変換する。
フロントエンドの Compute は収益化できない。

- 変換レート: **1 Insight = 1 Budget**
- 各カードの変換上限 = その **スループット** の値
- Insightプールが足りなければ、ある分だけ変換
- **手動処理**: プレイヤーが任意のバックエンド Compute カードを選び、Insight を割り当てる。割り当ての順序と量はプレイヤーが自由に決定できる

> 例: バックエンドに えくぼ (スループット 700) + むらた (スループット 500)。Insightプールに 1,200 あれば →
> プレイヤーは えくぼ に 700 Insight、むらた に 500 Insight を割り当てて、合計 Budget +1,200。Insight 残り 0。
>
> もし Insightプールが 400 しかなければ → プレイヤーは えくぼ に 400 Insight を割り当てて Budget +400（むらたには割り当てない）、または えくぼ に 200、むらた に 200 を割り当てる等、自由に配分できる。

### リソースフロー

```
DB/Object Storage（Backend） → Insight生成 → [Insightプール] → Backend Compute が変換 → Budget 回復
                                                                                          ↓
                                              メンテナンスコスト / SLAペナルティ / Strategy・Incident で消費
```

## 8. バトルのルール

### 基本ルール

**フロントエンドに配置されたコンピュート系リソース**カードは **1ターンに1回** 攻撃できる。**バックエンドのリソースは攻撃できない。**
**Object Storage をフロントエンドに置いた場合、そのカードは攻撃できない。**

1. 攻撃するカードを選ぶ
2. 相手の**フロントエンド**カード 1体を選んで攻撃
3. ダメージ = 自分の **スループット**
4. 相手の **可用性** からダメージを引く
5. 可用性が 0 以下 → **破壊**。相手の Budget から **SLAペナルティ** を引く

**重要なルール:**
- **攻撃にコストはかからない**（維持コストはターン終了時に別途徴収）
- **表向きになったターンから攻撃可能**（召喚酔いなし。ただしデプロイターン中は裏向きのため攻撃不可）
- **裏向きカードは攻撃対象にできない。** Frontend に裏向きカードしかいない場合、Backend を直接攻撃できる
- Cold Start はこのルールの例外ではなく、個別カード効果として記載がある場合のみ適用される（追加予定）
- **反撃なし:** 攻撃された側は自動反撃しない
- オーバーキル分のダメージは消失
- **可用性は自動回復しない。** Strategy / Attachment / Platform 効果でのみ回復可能
- 複数の Resource が同時に破壊された場合、**ターンプレイヤーのカードから順に**処理する。
 SLAペナルティは破壊されたカードごとに即座に適用される。

### バックエンドへの攻撃

バックエンドのカードは**通常は攻撃対象にできない**（コンピュート系、AI/ML系、DB系、オブジェクトストレージを問わず）。以下の場合のみ攻撃可能:

| 条件 | 説明 |
|------|------|
| **フロントエンドに表向きリソースが 0体** | 裏向き（デプロイ中）のカードがあっても、表向きリソースがいなければバックエンドを直接攻撃できる |
| **Incident** | 一部のインシデントはバックエンドを直接対象にできる |

> フロントエンドを全部倒す → バックエンドを直接攻撃できる → Insight生成が止まり収益化もできなくなる。
> **フロントエンドは「バックエンドを守る壁」。フロントエンドを崩すことが攻略の基本。**
> デプロイ中（裏向き）のカードは壁として機能しない——援軍が稼働するまでの隙を突かれないよう注意。

## 9. ゲームの流れ

### ターンとラウンド

各プレイヤーの行動順を **ターン** として個別にカウントする。

```
先攻 T1 → 後攻 T2 → 先攻 T3 → 後攻 T4 → …
```

- 先攻プレイヤーは常に**奇数ターン**（T1, T3, T5, …）
- 後攻プレイヤーは常に**偶数ターン**（T2, T4, T6, …）
- 先攻 + 後攻の **1巡 = 1ラウンド**（T1+T2 = ラウンド1、T3+T4 = ラウンド2、…）

### Phase 1: ドローフェーズ

1. リポジトリから **1枚** 引き、手札に加える
2. **デプロイターン経過処理:** 自分のフィールド上の裏向きカードのデプロイ残りターンを 1 減らす。0 になったカードは**表向き**になり稼働開始する。デプロイ時効果（TriggerDeploy）があればこの時点で発動する

### Phase 2: メインフェーズ

以下のアクションを**好きな順序・回数**で実行できる:

| アクション | 内容 | コスト |
|-----------|------|--------|
| **デプロイ** | 手札からカードをフィールドに出す。デプロイターンが 0 なら即表向き、1 以上なら裏向きで配置 | **無料** |
| **スケールアップ** | Resizable カードのランクを上げる | **無料**（メンテナンスコスト増） |
| **マイグレーション** | 表向きリソース間で移行を開始する（詳細は後述） | **無料** |
| **アタッチ** | Attachment を Resource に装備 | **無料** |
| **ストラテジー** | Strategy カードを使用 | カードに記載 |
| **インシデント** | 相手を妨害（**1ターン1枚**） | カードに記載 |
| **リアクティブ配置** | Reactive を Support Zone に伏せる | **無料** |
| **収益化** | Insight を Budget に変換する | **無料** |

**Insight生成は行われない（エンドフェーズに移動）。**

### Phase 3: バトルフェーズ

バトルを行うことができる。バトルのルールについては#8参照。

### Phase 4: エンドフェーズ

ターン終了処理を行う。
1. **維持コスト徴収:** フィールド上の全リソースの維持コストを Budget から差し引く
   - Non-Elastic: `MC = maintenance_cost × rank_multiplier`（small×1, medium×2, large×3）
   - Elastic: `MC = max(0, intrinsicStat - free_tier) × cost_per_request / 100`
     - `intrinsicStat = base × rank × family + effectiveElasticBonus`（Platform/パッシブ/アタッチメント/一時効果は除外）
     - `effectiveElasticBonus = free_tier × ln(1 + ElasticBonus / free_tier)`（対数逓減）
     - `free_tier` は固定値（Rank でスケールしない）→ Scale Up すると即座に MC 増加
     - `cost_per_request = 0`（Serverless 等）なら常に MC = 0
     - 例: Container (base TP=500, rank=small×1, ElasticBonus=500, free_tier=500, cost_per_request=10)
       → effectiveElasticBonus = 500 × ln(2) ≈ 346、intrinsicStat = 846、MC = (846 - 500) × 10 / 100 = **34**
2. 一時的な効果（「このターン中」など）の終了
3. **Yield生成:** バックエンドの各カードが自動的に Insight を生成し、Insightプールに加算する
4. 手札調整（上限 6枚になるように捨てる）
5. 相手にターンを渡す

### マイグレーション（リソース移行）

既存リソースを **SLA ペナルティなし**で安全に退役させる仕組み。現実のブルーグリーンデプロイや段階的移行に相当する。

**条件:**
- 新リソースが既にフィールドで**表向き（稼働中）**であること
- 旧リソースが**表向き（稼働中）**であること
- 新リソースの **デプロイターン >= 旧リソースのデプロイターン**（ダウングレード不可）

**フロー:**
1. マイグレーションを開始する（メインフェーズのアクション）
2. **新リソースはロック状態**になる（攻撃・Yield 生成・収益化など全て不可）
3. **旧リソースは通常通り稼働**し続ける
4. **1ターン経過**後、マイグレーション完了（Platform 効果で短縮可能）

**完了時:**
- 旧リソースを破棄する（**SLA ペナルティなし**）。旧スロットが空く
- 新リソースのロックが解除され、通常稼働

**移行中に旧リソースが破壊された場合（マイグレーション失敗）:**
- **SLA ペナルティが発生**する（旧リソースの破壊分）
- 新リソースはロック解除され、そのまま稼働を開始する
- ストーリー: 引き継ぎに失敗してユーザー影響を出したが、新サービスは稼働開始した

**ダウングレード禁止の理由:**
K8s → Serverless への移行で SLA ペナルティを回避する「事業縮小」は、ゲームのストーリー（事業を成長させる）に反する。ダウングレードが必要な場合は、従来通り旧リソースを破壊（SLA ペナルティあり）して対応する。

| 方法 | 所要ターン | SLA ペナルティ | ダウンタイム |
|------|-----------|-------------|------------|
| **即破壊＋再デプロイ** | 新カードのデプロイターンのみ | **あり** | **あり** |
| **マイグレーション** | デプロイターン + 1 | **なし** | **なし** |

### 先攻プレイヤーの制限（T1 のみ）

先攻の **T1**（ゲーム最初のターン）は **Draw + Main Phase + End Phase のみ**。
収益化（メインフェーズ内の distribute_yield アクション）、Battle Phase をスキップする。
**インシデントカードも T1 では使用できない。** 相手がサポートカードを配置する前に一方的に妨害できてしまうのを防ぐため。
後攻の T2 以降は全フェーズ・全カードが有効。

（Insight生成はエンドフェーズに行われるため、T1 終了時にも生成される。T3 まで Insightプールで保持される）

## 10. ゲームの終了

以下のいずれかが起きたらゲーム終了:

1. **Budget 0 以下（Budget Zero）** — そのプレイヤーが**敗北**（破産）
2. **表向きリソース 0 体（System-Down）**（稼働実績あり） — そのプレイヤーが**敗北**（システムダウン）
3. **自分の 3 ターン目終了時に稼働実績なし（Launch Failure）** — そのプレイヤーが**敗北**（ローンチ失敗）
4. **リポジトリ 0枚（Repository Out）** — そのプレイヤーが**敗北**（リポジトリアウト）
5. **ターンリミット（Turn Limit / T30）** — 15ラウンド経過後、Budget が多い方が勝利。同額なら Draw（引き分け）
6. **タイムアウト（Timeout）** — タイムバンクが 0 になったプレイヤーが**敗北**（詳細はセクション12参照）

> **システムダウン:** フロントエンド・バックエンドを問わず、フィールド上の**表向き** Resource が全て失われた時点で即敗北。
> 裏向き（デプロイ中）のカードはカウントしない——援軍が構築中でも、稼働中のシステムが全滅すればゲームオーバー。
> 手札にカードがあっても間に合わない——インフラが完全停止した瞬間にゲームオーバー。
> **稼働実績フラグ:** 一度でも表向きリソースがフィールドに存在したら `true` になる。System-Down はこのフラグが `true` のプレイヤーにのみ適用される。
>
> **ローンチ失敗:** 自分の 3 ターン目（先攻なら T5、後攻なら T6）のエンドフェーズ終了時に、一度も表向きリソースが存在しなかった場合に敗北。
> 投資家から 3 ターン分の猶予をもらったが、サービスを立ち上げられなかった——資金は引き上げられ、スタートアップは解散。
>
> **Draw（引き分け）:** Turn Limit（T30）到達時に両者の Budget が同額だった場合のみ発生する特殊ケース。

## 11. その他のルール

### 端数処理

倍率計算の結果が整数にならない場合、**1 の位で切り捨てる**（1 未満切り捨て）。

> 例: 可用性 1,350 を半分 → 675（端数なし）
> 例: 可用性 1,350 × 0.7 → 945

### 効果の回数制限

カード効果に回数制限の記載がない場合、**回数無制限**で使用できる。

回数制限がある効果は「1ゲーム中に1回」「1ターン中に1回」等、効果テキストの末尾に明記される。

### コスト軽減の下限

カード効果によってコストが軽減される場合、**コストは 0 未満にはならない**。

> 例: 維持コスト 300 のカードに「維持コスト -200」と「維持コスト -200」の効果が両方適用される場合 →
> 300 - 200 - 200 = -100 ではなく、**0** となる。

## 12. 詳細ルール

### チェーンシステム

このゲームでは、遊戯王のチェーンシステムに準拠したルールを採用する。

**チェーンの基本:**
- 行動やカード効果に対して、リソースの誘発効果やリアクティブカードが**自動的にチェーンに積まれる**
- チェーンは「後入れ先出し（Last In, First Out）」で解決される
- **重要**: リアクティブカードに対して、別のリアクティブカードをチェーンすることは**できない**（カウンター罠相当のカードは存在しない）
- **最大チェーン数**: **3**（行動 → リソース効果 → リアクティブ）

**チェーンの例:**
1. プレイヤーAが「DDoS Attack」（Incident）を使用
2. プレイヤーBのサポートゾーンに伏せてあった「Rate Limiter」（Reactive）が**自動発動**してチェーンに積まれる
3. プレイヤーBのリソース（例: 攻撃時効果を持つカード）の誘発効果も**自動的に**チェーンに積まれる
4. チェーン解決（LIFO）: リソース誘発効果 → Rate Limiter → DDoS Attack の順で解決
5. リアクティブに対して、さらにリアクティブをチェーンすることはできない

### アタッチメントのルール

**装備スロット:**
- 各 Resource は **アタッチメントスロットを 2 つ** 持つ。1体の Resource に装備できる Attachment は**最大 2枚**まで
- スロットが埋まっている場合、新たに装備することはできない（既存の Attachment を外すことはできない。装備先の破壊・バウンス等でのみ外れる）

**装備と破壊:**
- Attachment は Resource に装備コスト **0（無料）** で装備できる
- 同じ Attachment を複数装備することは**可能**。ただし、カードに「同名カードは1枚まで」等の記載がある場合はそれに従う
- 装備先の Resource が破壊されるか、フィールドを離れた場合、装備されていた全ての Attachment は**トラッシュに送られる**
- この方法でトラッシュに送られた Attachment は「**破壊された**」として扱う

### 効果の持続期間

効果テキストに記載された持続期間の定義:

| 表記 | 内部 Duration | 意味 |
|------|--------------|------|
| **このターン** | `this_turn` | 現在の自分のターン終了まで |
| **次のターン終了まで** | `until_next_turn_end` | 次のターン（＝相手のターン）終了まで |
| **次の自分のターン終了まで** | `until_next_own_turn_end` | 次の自分のターン終了まで（全体で3ターン後に終了） |

> `until_next_own_turn_end` の計算方法: 自分のターンで N ターン = 全体で (2N-1) ターン。
> - 自分のターンで2ターン = 全体3ターン（自分→相手→自分で終了）
> - 自分のターンで3ターン = 全体5ターン（自分→相手→自分→相手→自分で終了）
>
> 例: 「このターン、スループットを +200 する」→ 現在の自分のターンのみ有効
> 例: 「次の自分のターン終了まで、Yield を +400 する」→ 次の自分のターン終了まで有効（相手のターンを跨いで継続）

### 効果の適用タイミング

**常時効果:**
- 全ての継続効果は、フィールドの状態に基づいて**常時再計算**される
- 条件を満たした瞬間に効果が適用され、条件を満たさなくなった瞬間に効果が消失する

> 例: 「場に SHE カード 3枚以上でスループット +200」→ SHE カードが 3枚になった瞬間にスループット +200、2枚以下になった瞬間に効果消失

### サーチ効果の失敗

**対象が見つからない場合:**
- サーチ効果で対象が見つからない場合でも、**コストは支払われる**
- 例: Cloud Engineer / Cloud Architect で2枚ドローし、両方とも調律部カードだった場合 → 両方ともトラッシュに送られる（調律部デッキには採用されない想定）

### バウンス（手札に戻す）

**カードが手札に戻った場合:**
- Resource が手札に戻った場合、全ての変更がリセットされる:
  - Rank は small に戻る
  - 全てのダメージが除去される
  - Instance Family の選択がリセットされる
  - ElasticBonus がリセットされる（base に戻る）
  - 装備されていた Attachment は全てトラッシュに送られる（破壊扱い）

### ターンタイマー

遊戯王マスターデュエルの仕様に準拠したターンタイマーを採用する:

- 各プレイヤーは**タイムバンク**を持つ（例: 8分）
- 各アクションには短いタイマーがある（例: 30秒）
- 自分のターン中、タイムバンクが減少する
- タイムバンクが 0 になったプレイヤーは**敗北**（Timeout。#10 の勝利条件6）

> 詳細な時間設定は実装時に調整可能
