# クライアント動作確認方針

## 概要

クライアントの動作確認には「モックのみ（クライアント単体）」と「ローカル結合（サーバー接続）」の 2 つの手段がある。
それぞれの得意・不得意を踏まえ、目的に応じて使い分ける。

## 比較表

| 項目 | モックのみ (クライアント側) | ローカル結合 |
| --- | --- | --- |
| UI レイアウト確認 | ○ | ○ |
| 画面遷移 | ○ | ○ |
| バトルのフェーズ進行 | △ モック game_state を手動で作る必要あり | ○ サーバーエンジンが正確な状態を返す |
| NPC 対戦フロー | × | ○ 既存 NPC AI でそのまま動く |
| WebSocket 双方向通信 | △ 再現困難 | ○ |
| 型の整合性確認 | × ズレに気づきにくい | ○ 実際の JSON で検証 |
| セットアップコスト | なし | サーバーにローカルモード追加が必要 |

## モックのみ（クライアント単体）

### 用途

- UI コンポーネントの見た目・レイアウト調整
- 画面遷移フローの確認
- アニメーション・インタラクションの検証

### 方法

DevPage (`/dev`) から以下のモック状態を注入できる:

- `mainPhaseMyTurn()` — メインフェーズ（自分のターン）
- `battlePhaseMyTurn()` — バトルフェーズ（自分のターン）

モックデータの定義: `src/test/mocks/mockGameState.ts`

### 制約

- ゲームロジック（フェーズ進行、Budget 消費、ダメージ計算等）はクライアントに存在しないため、手動でモック状態を切り替える必要がある
- WebSocket 通信のテストはできない
- サーバー側の型変更に追従できず、型のズレに気づきにくい

## ローカル結合（サーバー接続）

### 用途

- バトルフェーズの進行テスト
- NPC 対戦による一連のゲームフロー検証
- WebSocket メッセージの送受信確認
- クライアント・サーバー間の型整合性チェック

### 前提条件

- Go サーバー (`overload-party-server`) をローカルで起動
- サーバーにローカルモード（認証スキップ等）の追加が必要
