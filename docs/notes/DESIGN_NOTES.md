## 設計哲学

### Budget 経済がゲームの核心

DB/Object Storage → DV 生成 → Compute が Budget に変換。このパイプラインが収益源。
Budget を攻撃に使うか、配置に使うか、温存するか — すべてが Budget の配分判断。
Resource を壊されるとSLAペナルティで Budget が減る。攻撃されなくても Budget を浪費すれば自滅する。

**「インフラ投資 vs 攻撃 vs 生存」の三つ巴がゲームの核心。**

### スループットの二重用途

スループット（Throughput）は攻撃力と Revenue 変換上限を兼ねる。

- スループットが高い = 稼ぎもいいが壊されやすい
- AI/ML (スループット 1,200) は Revenue も最高だが可用性 1,000 で脆い
- この二重用途により、「攻撃力が高いカードは経済力も高い」という自然なバランスが生まれる

### SLAペナルティの設計

強いカードほどSLAペナルティが高い → 破壊されるリスクも高い。
Budget は統一リソースなので、SLAペナルティは**行動資金とライフの両方を削る**。壊されるほど行動もできなくなる悪循環。

> 「Exadata (SLAペナルティ 800) を出せば DV は稼げるが、壊されたら Budget -800」という判断が生まれる。

## Elastic の設計意図

### フロントエンド Elastic のジレンマ

大ダメージを受けるほど強くなる = 相手に「攻撃すれば強化させる」ジレンマを与える。フロントエンド Elastic を攻撃して強化させるか、無視して自由に使わせるか。

### Orchestrator（R+E）の設計

K8s の「ノードサイズ変更（手動）+ HPA による Pod 自動スケール」を忠実に再現。最も柔軟で強力。ただし開発コストとSLAペナルティも最高クラスでリスクも高い。

### バックエンド Elastic（NoSQL）

Revenue パイプラインが回り始めれば自然に上限に達する設計。DV 消費量 = データ需要が高い → NoSQL が自動スケールする、というクラウドの挙動を再現。

## ゾーン配置の設計意図（v1.6〜）

### なぜ Object Storage をフロントエンドに置けるようにしたか

現実のクラウドアーキテクチャでは、S3 Static Website Hosting や Azure Blob の静的配信など、**Object Storage がフロントエンドとして機能するケース**が多い。
これを反映し、Object Storage をフロントエンドに配置できるようにした。

ただし静的ホスティングは「攻撃しない壁」であるため、**フロントエンドに置いた Object Storage は攻撃不可**。高い可用性を活かした防御専用ユニットとして機能する。

### なぜバックエンドに Compute を置けるようにしたか

現実のアーキテクチャでは、API サーバーやバッチ処理サーバーが**バックエンドに存在し、データを処理して価値（DV）を Budget に変換する**。
フロントエンドは「ユーザーからのリクエストを受ける窓口」であり、収益化はバックエンドの Compute が担う。

この構造を再現することで、**「どこに Compute を置くか」という配置戦略**が生まれる:
- **フロントエンド Compute**: 攻撃に特化。収益化はできないが相手を直接削れる
- **バックエンド Compute**: 収益化できる。ただしフロントエンドが全滅するまで攻撃されない安全地帯にいる

### バックエンドの攻撃保護

バックエンドのカードは コンピュート系リソース・データ系リソースを問わず、相手のフロントエンドが存在する限り攻撃対象にできない。
これにより「フロントエンドを崩すことが攻略の基本」という構造は維持される。

## インフラ基盤の選定ログ

### Cloud Run + Redis vs GKE Autopilot

リアルタイム対戦（WebSocket常時接続）に適したインフラ基盤を選定するため比較を行った。

> 料金は2025年前半時点のGCP公式情報に基づく概算。最新値は [GCP Pricing Calculator](https://cloud.google.com/products/calculator) で確認のこと。

**月額コスト概算（asia-northeast1、24h稼働）:**

| 構成要素 | Cloud Run + Redis (5K) | Cloud Run + Redis (10K) | GKE Autopilot (5K) | GKE Autopilot (10K) |
|---------|------|------|------|------|
| コンピュート | ~$305 | ~$609 | ~$159 | ~$318 |
| Redis (Standard 3GB) | ~$147 | ~$147 | 不要 | 不要 |
| VPC Connector | ~$30 | ~$40 | 不要 | 不要 |
| クラスタ管理料 | — | — | $73 | $73 |
| LB | 内蔵($0) | 内蔵($0) | ~$18 | ~$18 |
| **合計** | **~$482** | **~$796** | **~$250** | **~$409** |

> ピーク8h/日運用の場合、Cloud Run部分は約1/3に削減可能（ゼロスケールの利点）。

**6軸比較:**

| 比較軸 | Cloud Run + Redis | GKE Autopilot |
|--------|---------------------|---------------------|
| **コスト** | Redis + VPC Connectorの固定費が上乗せ。ピーク時間が短い場合は有利 | 24h稼働ではRedis不要な分安い |
| **WebSocket制約** | タイムアウト上限**60分**。再接続ロジック必須。SIGTERM猶予10秒 | **制限なし**。PodDisruptionBudgetでドレイン制御可能 |
| **スケーラビリティ** | 自動スケール優秀だがWebSocketドレインが課題 | HPA + PDB で接続保護。Agones統合可能 |
| **運用難易度** | **低い**。ただしRedis監視が別途必要 | **中**。Autopilotでノード管理不要だがK8sマニフェスト管理が必要 |
| **レイテンシ** | 異インスタンスの2人はRedis経由で**+0.5〜2ms** | 同一Pod内で対戦完結すれば**ゼロオーバーヘッド** |
| **開発の複雑さ** | **高い**。Redis Pub/Sub、インスタンス間状態同期、60分タイムアウト対策を自前実装 | **低〜中**。同一Pod対戦ならPod間通信不要 |

**結論:** GKE Autopilot を採用。詳細は ARCHITECTURE.md §3.2 を参照。

> Cloud Run を選ぶべきケース: K8s知識なし、ユーザー数が不安定で0接続時間が長い、MVP優先の場合。

### Spanner書き込みコスト分析

| 項目 | 全アクション書き込み | インメモリ + 30秒CP |
|------|---------------------------|---------------------------------------|
| 1試合あたりの書き込み | 100回 | 22回（開始1 + CP20 + 終了1） |
| 書き込みレート（同時1,000試合） | ~167 writes/sec | ~37 writes/sec |
| 必要PU | 200-300 PU | **100 PU** |
| Spanner月額 | ~$170-$255 | **~$85** |
| データ安全性 | 最高 | 中（最大30秒分ロスト。クライアント側イベントソーシングで復元） |

> Spanner の mutation は**カラム単位**でカウント。JSON型カラムの更新は1 mutation。GameStates 1回の UPDATE は約2-3 mutations。

**結論:** 全アクション直接書き込み（方式A）を採用。月額差 $85〜$170 でPodを完全ステートレスにでき、データロストゼロ・アーキテクチャ簡素化のメリットがコストを大きく上回る。カードゲームのレイテンシ要件（+5-10ms）も問題なし。
