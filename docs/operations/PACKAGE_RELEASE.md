# パッケージのリリース手順

各リポジトリの `packages/` 配下にある共有パッケージ (Go module タグ・NuGet・npm) を発行するときの手順。バージョン番号の上げ幅 (patch / minor / major) の判断基準は共通ルール (keyandnotes-rules の principles「バージョニング」) に従う。本書はその判断を発行の操作に落とすときの手順を扱う。

## 発行方式の見分け方

発行の仕組みはリポジトリにより 2 方式ある。どちらかは対象リポジトリの `.github/workflows/publish.yaml` の `on:` を見て判断する。

- **手動のみ方式**：`workflow_dispatch` だけのリポジトリ。マージしても発行されない。
- **自動併用方式**：`push: main` (packages 配下の paths 条件) でも発火するリポジトリ。パッケージに差分のあるマージのたびに、自動で patch として発行される。

## 手動のみ方式の手順

1. 変更をマージする (この時点では何も発行されない)
2. 発行したいタイミングで `publish.yaml` を `workflow_dispatch` で実行する。`target` に対象パッケージ、`bump` に上げ幅を指定する

## 自動併用方式の手順

patch の変更は、マージによる自動発行だけで完結する。手動操作は不要。

上げ幅が minor / major の変更は、次の順で発行する。

1. 変更をマージする。自動発行が走り、**同じ内容がまず patch 版として発行される**。これは止めなくてよい
2. `publish.yaml` を `workflow_dispatch` で実行する。`bump` に minor / major を、`target` に対象パッケージ名を明示する。対象が複数パッケージなら 1 つずつ実行する
3. 同じ内容の minor / major 版が追加発行される。利用側にはこちらを参照させる

### 自動発行が patch 固定である理由

push イベントには入力を渡せず、変更が後方互換かどうかを機械では判定できない。上げ幅の判断は人にしかできないため、自動発行は最小の上げ幅に固定し、minor / major は人の手動実行に分離している。

### 同じ内容の 2 バージョンが並ぶことを許す理由

発行はタグ (`packages/<パッケージ名>/vX.Y.Z`) として main のコミットに残る。同じ内容かどうかは次が空であることで機械的に確認できるため、追跡性は失われない。

```
git diff packages/<パッケージ名>/v<旧> packages/<パッケージ名>/v<新> -- packages/<パッケージ名>/
```

利用側はバージョンを固定して参照するので、参照されない patch 版が残ることに実害はない。自動発行を止めてから手動発行する代替 (workflow の一時無効化や実行の取り消し) は、戻し忘れや競合で壊れやすいため採らない。

### 手動実行で `target` を明示する理由

`target` を省略 (auto) すると「パッケージの最新タグとの差分があるもの」だけが発行対象になる。自動発行が先に走った後は差分ゼロと判定され、**何も発行されずに終わる**。`target` にパッケージ名を明示すると差分判定を通らず必ず発行される。

## 実行前の注意

`workflow_dispatch` の入力仕様はリポジトリで差がある。`target` 入力が無いリポジトリでは、手動実行がそのリポジトリの全パッケージを対象にするものがある。実行前に対象リポジトリの `publish.yaml` の入力定義と発行対象を確認する。
